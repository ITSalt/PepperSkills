# Pepper Orchestrator

> **Preview (0.9.1).** Режимы `init`, `plan`, `dispatch`, `review`, `verify`, `deliver`, `resume`, `owner`, `decide`,
> `close`, `reopen`, `report`;
> потоки в одном репозитории с worktree и замками; облачные сессии; сгенерированные настройки сессий.
> Форматы и команды могут измениться до 1.0.0.

Портативный Agent Plugin для концепции единого оркестратора (hub-and-spoke): одна сессия
оркестратора планирует работу в нескольких репозиториях, пишет пакеты работ для сессий модулей,
проверяет их результат и хранит всё состояние в версионируемых Markdown-файлах. Merge, деплой,
PROD и запись в БД остаются за владельцем — в виде готовых однострочных команд.

Установка и обновление: [инструкция](../../docs/installation-and-updates.ru.md) ·
[English](../../docs/installation-and-updates.md).

```text
/plugin marketplace add ITSalt/PepperSkills
/plugin install pepper-orchestrator@pepperskills
```

## Использование

Фраза «спланируй X по концепции единого оркестратора» или короткие команды:

| Команда | Что делает |
|---------|------------|
| `/pepper-orchestrator:init <program>` | рабочее пространство `features/<program>/` и `orch.yaml` |
| `/pepper-orchestrator:plan <задача>` | факты → план → пакеты работ → вопросы владельцу |
| `/pepper-orchestrator:dispatch <WP>` | проверка пересечений и замков, команда запуска |
| `/pepper-orchestrator:review <WP> [PR]` | автоматические находки, агент-рецензент, вердикт, отчёт |
| `/pepper-orchestrator:deliver <WP>` | доверенная доставка (по вашему решению): ворота, merge, стенд, проверка |
| `/pepper-orchestrator:verify <WP> --env test\|prod` | run деплоя, отдаваемая версия, команды проверки, живой сценарий |
| `/pepper-orchestrator:resume` | чтение состояния, сверка с реальностью, следующий шаг |
| `/pepper-orchestrator:owner` | очередь владельца с командами; «готово» → сверка и закрытие |
| `/pepper-orchestrator:close [итог]` | цель достигнута: проверка завершения, итоговый отчёт, архив |
| `/pepper-orchestrator:reopen <причина>` | открыть снова закрытую программу, цель которой не достигнута |
| `/pepper-orchestrator:report [что]` | сообщить о дефекте плагина: обезличенная запись, Issue после вашего «да» |
| `/pepper-orchestrator:decide <текст>` | решение D-n / допущение A-n / вопрос Q-n или вопрос владельцу P-n |

Версия 0.9.1 — preview (этапы 2a–2e, 3a, 3b, 3e, 3c). Модуль — весь репозиторий либо раздел или домен одного
репозитория: каждый поток работает в своём worktree (`claude -w`), общие пути и ресурсы держатся
замками, слияния в один репозиторий идут очередью. `review` на первой сдаче запускает агента-рецензента
(только чтение, одноразовый клон), на пересдачах читает дифф ревизии. `verify` проверяет стенд и прод по
фактам. Режимы release, retro и PreToolUse-хуки появятся в следующих версиях; до тех пор скилл ведёт эти шаги
по концепции инструкциями.

## Сценарии работы

Локально — короткие команды (`/pepper-orchestrator:plan ...`); в облачной сессии команд плагина нет:
вызывайте `/pepper-orchestrator <режим> ...` или фразой.

1. **Новая программа, отдельный домашний репозиторий.** `init <program>` (ответ на вопрос о виде сессий) -> `plan <задача>` -> ответы
   на вопросы владельцу через `decide` -> `dispatch <WP>` -> владелец запускает сессию модуля по
   выданной команде или промпту -> сессия открывает PR -> `resume` находит его -> `review <WP>` ->
   владелец мержит -> «R-n готово» в `owner` -> оркестратор сверяет по факту и закрывает.
2. **Новая программа в облаке, один репозиторий.** Облачная сессия на базовой ветке:
   `/pepper-orchestrator init <program> --in-repo <repo-id>` — создаёт и пушит ветку
   `orch/<program>`. Дальше **каждая** облачная сессия оркестратора стартует на `orch/<program>`
   (ветка выбирается при запуске сессии).
3. **Каждая следующая сессия.** `resume`: локально — в домашнем репозитории, в облаке — на
   `orch/<program>`. Повторный `init` не нужен: на существующем пространстве скилл сам переходит к
   `resume`. Стартовый текст новой сессии — `orchestration/bootstrap-prompt.md`.
4. **План уже есть.** Передайте его текст или путь в `plan` — он превратит его в пакеты работ.
   Повторный `plan` — пере-план: ID сохраняются, пакеты добавляются или отменяются.
5. **Новая работа в существующей программе.** `plan <задача>`, а не `init`.
6. **Сессии модулей.** `dispatch` выдаёт команду для терминала (`claude -w <slug>` для потока общего
   репозитория) или промпт для новой облачной сессии на базовой ветке. Модуль сдаёт PR с ID пакета
   в теле. Готовность оркестратор узнаёт из сообщения READY, где сообщения работают, иначе — по PR и
   запушенной ветке (`resume`, `orch.py ready`).
7. **Очередь владельца.** `owner` показывает действия и вопросы командами; «R-3 готово» —
   оркестратор сверяет и закрывает; `decide <текст>` записывает ответы владельца.
8. **Параллельные потоки в одном репозитории.** Модули — разделы или домены одного репозитория со
   своими путями; общие пути и ресурсы берутся замками, слияния идут очередью (концепция, §7 и §12).
9. **Обновление.** Локально в терминале `claude plugin update pepper-orchestrator@pepperskills` или в
   сессии `/plugin` -> Installed -> плагин -> Update now; для сторонних маркетплейсов, как этот,
   автообновление по умолчанию выключено. В облаке — изменить строку-комментарий во фрагменте
   setup-скрипта ниже, чтобы окружение пересобралось.
10. **Цель достигнута -> `close`.** Одна программа — одна цель: когда условие завершения из
    `PLAN.md` выполнено, запустите `close` (он проверяет пакеты, PR, замки и пункты владельца по
    фактам; хвосты переносятся `orch.py owner carry <id> "<причина>"`), а следующую цель начните
    новой программой через `init`. В режиме in-repo владелец выполняет напечатанные команды тега и
    удаления ветки.
11. **Проверка стенда и прода по фактам.** После вашего merge (и выкладки стенда или прода)
    `verify <WP> --env test` проверяет run деплоя для merge-коммита, версию, которую отдаёт окружение
    (`version_url`), и читающие команды `verify_test` репозитория, затем проходит критерии приёмки пакета
    живым сценарием. PASS даёт `VERIFIED_TEST` (после релиза `--env prod` даёт `PROD`); FAIL оставляет
    статус и пишет дефект в `bugs/`. `orch.py verify --list` показывает, что ждёт проверки; в релиз идут
    только пакеты `VERIFIED_TEST`.
12. **Поток получил отказ.** Сессия не обходит его, а присылает
    `QUESTION <WP> :: отказ: <точный текст> :: ref=<команда>`. Оркестратор отвечает по фактам:
    недостающее узкое правило (команда тестов, генератор) — в `orch.yaml` и `orch.py settings <модуль>`,
    затем сессия перезапускается той же командой (или вы отвечаете на запрос в её окне); действие
    только владельца (merge, деплой, прод) — пункт владельцу. «Классификатор недоступен» — не
    вердикт: сессия повторяет позже.
13. **Доверенная доставка.** По умолчанию мержите и деплоите вы. Если вы так решите (`decide`, затем
    `orch.py delivery set merge orchestrator --decision D-n` и `stand`), оркестратор доставляет каждый принятый
    пакет: `orch.py accept <WP> <sha> --report <отчёт>` фиксирует проверенную ревизию, `deliver --check` показывает
    ворота G1–G10 по фактам (принятая ревизия, head PR, проверки, mergeable, очередь слияний и замки, проверки
    репозитория, блокирующие пункты владельца, граф, режим включён и нет стопа), `deliver --apply` сливает штатным
    методом репозитория (никогда `--admin`), ждёт run выкладки стенда, проверяет его и ставит `VERIFIED_TEST`. Сбой
    ставит доставку на стоп с дефектом и текстом REVISE; `orch.py hold "<причина>"` или `delivery.<уровень>: owner`
    останавливает её в любой момент. Каждая доставка — строка в `release/deliveries.md`. Прод в этой версии — ваш.
14. **Плагин сломался — сообщи.** Если неверен сам плагин (ошибка скрипта, неверное сгенерированное
    правило), оркестратор продолжает программу обходным путём и запускает `report`: `orch.py report --check`
    пишет обезличенный `bugs/PLUGIN-BUG-<n>.md` (имена вашей программы, модулей, сессий и репозиториев,
    пути, адреса, e-mail, токены и термины вашего `.private-terms.local` из .gitignore заменяются
    плейсхолдерами) и показывает текст Issue. После вашего явного «да» `orch.py report --apply --confirmed`
    комментирует найденный похожий Issue в ITSalt/PepperSkills или открывает новый (метки `bug`,
    `from-agent`, `needs-triage`); при `bug_reports: auto` и вашем решении D-n — без вопроса. Уязвимости —
    через SECURITY.md. `resume` показывает отчёты и сообщает, если доступна новая версия плагина.

## Права сессий и режим разрешений

- **Режим разрешений.** `init` спрашивает, в каком режиме работают сессии программы (`auto`
  рекомендуется, либо `acceptEdits`, `default`, `dontAsk`, `bypassPermissions`), и пишет
  `permission_mode`.
- **Файлы настроек.** `orch.py settings all` пишет `orchestration/settings/<модуль>.json` для каждого
  локального модуля и `orchestrator.json`: узкие allow-правила (чтение репозитория и рабочего
  пространства, `cat`/`grep`/`rg`/`sed -n`/…, git status/diff/log/add/commit/switch, `gh pr
  create`, тесты, проверки и подготовка worktree модуля дословно), deny-правила (merge,
  force push и push в базу в обычных формах, `gh workflow run`, `gh release`, MCP прода и команды деплоя в прод,
  правка рабочего пространства оркестратора, запрещённые команды методологии как `Skill(<имя>)`),
  контрольные точки владельца как ask-правила (`checkpoints`, по умолчанию `deploy_test`),
  `autoMode.environment` (`$defaults` плюс доверенный репозиторий) и `crossSessionInbound: accept`.
  Allow-правила для `git push` нет: хвостовой `*` совпал бы и с `<ветка>:<база>`, и с force-флагами,
  поэтому push решает классификатор (или спрашивает вас при контрольной точке `push`).
  Команда идемпотентна; ваши дополнения — в `<имя>.local.json`, который она не трогает, а `dispatch`
  не подставляет.
- **Команды запуска.** `dispatch` добавляет в каждую локальную команду `--permission-mode <режим>
  --settings <абсолютный путь>` и отказывает, пока файла нет; `init` печатает команду оркестратора:
  `cd <рабочее пространство> && claude --name <program>-coord --permission-mode <режим> --settings
  orchestration/settings/orchestrator.json`. Облачные сессии берут права из облачного окружения.
- **Доставка сообщений.** Без `crossSessionInbound: accept` сообщения между сессиями разных классов
  режима (обход подтверждений против auto, acceptEdits, dontAsk, default) ждут вашего одобрения в
  окне получателя и через 5 минут удаляются. Альтернатива для всех ваших сессий: `/config` ->
  «Messages from your other sessions» -> accept. Протокол не полагается на сообщения: READY находится
  и по PR и запушенной ветке.
- **Worktree без секретов.** `worktree_setup` — только установка зависимостей и генерация.
  Gitignored-файлы, нужные worktree, — в `.worktreeinclude` в корне репозитория (Claude Code копирует
  их в каждый новый worktree; `init` предлагает содержимое вопросом владельцу), а
  на macOS и Linux `.claude/settings.local.json` каждый worktree читает из основного checkout (на Windows —
  нет; правила сессии всегда приходят из `--settings`). `lint` предупреждает о
  `cp`/`rsync`/`ln` файлов `.env*`, каталогов secret/key/cert и `.claude/`.
- **Замки по запросу.** Ресурс `{name: ci-gate, mode: on-demand}` не держится весь пакет: сессия
  присылает `LOCK ci-gate`, оркестратор берёт его `orch.py lock acquire` (или ставит пакет в
  очередь), `UNLOCK` или READY отдаёт; `lint` предупреждает о замке старше `lock_stale_hours`
  (по умолчанию 4).
- Правила — ограждение для обычных форм команд (`git -C . push` — не `git push`), а не граница
  безопасности: ею служат защита веток и хуки.

## Windows

- **Пути в правилах.** Файлы настроек используют форму, которую документация Claude Code описывает для
  Windows: пути перед сравнением приводятся к POSIX, поэтому `C:\projects\x` в правилах `Read`/`Edit` —
  `//c/projects/x`. Сетевые (UNC) пути отклоняются: подключите ресурс буквой диска или работайте из
  локального клона.
- **Команды.** Bash-правила сравниваются с текстом команды, поэтому запускайте скрипты с прямыми
  слэшами, как их пишут правила: `python3 C:/.../scripts/orch.py ...`; настройки оркестратора разрешают
  и `python ...`, и `py -3 ...` (на Windows `python3` может отсутствовать).
- **Оболочка.** На Windows `init` спрашивает, из PowerShell или bash вы запускаете сессии, и для PowerShell
  пишет `shell: powershell`; `init` и `dispatch` тогда печатают `cd "<каталог>"; claude ...`.
- **Worktree.** На Windows worktree не читает `.claude/settings.local.json` основного checkout; плагин
  передаёт правила каждой сессии через `--settings`, копировать ничего не нужно.
- Вывод и текст процессов — в UTF-8 при любой кодовой странице (с 0.9.1): `PYTHONUTF8` и
  `PYTHONIOENCODING` больше не нужны.
- Пока нет: Windows-раннера в CI и PowerShell-форм Bash-правил (backlog).

## Модели и окружение

- **Вид сессий.** `init` спрашивает, работают ли сессии модулей локально (рекомендуется) или в
  облаке; для облака нужно имя вашего облачного окружения. Оркестратор в облаке работает только с
  облачными сессиями.
- **Модель реализатора.** В каждом пакете — Модель, Усилие и Почему такая модель, из `orch.yaml`
  (`models.implement`, `model`/`effort` модуля); для рискованных пакетов оркестратор рекомендует
  `opus` + `high` (`orch.py model <WP> opus --effort high --reason "..."`). Локальные команды
  запуска несут `--model`/`--effort`; облачные пакеты — блок с окружением, моделью, усилием и
  ссылкой предзаполнения claude.ai/code. С третьего раунда сверки оркестратор предлагает
  перезапуск на `models.escalate`.
- **Не** набирайте `/model <имя>` с аргументом в локальной сессии, чтобы сменить модель модуля: это
  станет вашим умолчанием для всех новых сессий. Используйте флаги запуска или пикер `/model` и `s`.
  Не задавайте `ANTHROPIC_MODEL` в облачном окружении, общем с оркестратором, и не кладите секреты
  в переменные окружения.
- Агенты: `orchestrator-scout` работает на Opus; `orchestrator-reviewer` и `orchestrator-verifier` — на модели оркестратора.

## Облачные сессии

Облачные сессии (claude.ai/code) не ставят плагины из проектных настроек, а писать в `.claude/`
облачной сессии нельзя. Скилл им даёт **setup-скрипт** облачного окружения: он выполняется до старта
Claude, записанные им файлы остаются в окружении:

```bash
# pepper-orchestrator skill (PepperSkills); change this comment to refresh the cached environment.
# A failure here must not block the environment: the subshell reports it and setup continues.
(
  set -e
  pepper_dir="$HOME/.cache/pepperskills"
  if [ -d "$pepper_dir/.git" ]; then
    git -C "$pepper_dir" pull --ff-only -q
  else
    git clone -q --depth 1 https://github.com/ITSalt/PepperSkills "$pepper_dir"
  fi
  bash "$pepper_dir/scripts/install-skill.sh" pepper-orchestrator
) || echo "pepper-orchestrator: skill not installed; setup continues" >&2
```

Ненулевой код setup-скрипта не даёт стартовать ни одной сессии окружения, поэтому фрагмент не падает:
ошибка клона или установки печатается, и setup продолжается без скилла.
`install-skill.sh` идемпотентен: копирует `plugins/<name>/skills/<name>` в
`~/.claude/skills/<name>` (или в `--dest`) и печатает версию. После первого запуска окружение
кэшируется, поэтому скилл обновится при изменении setup-скрипта или истечении кэша.

Команд плагина в облаке нет: вызывайте `/pepper-orchestrator <режим> <аргументы>` (например,
`/pepper-orchestrator resume`) или фразой. Облачная программа держит рабочее пространство в самом
репозитории на ветке `orch/<program>` (`init --in-repo`), сессии модулей — облачные, их запускают по
промпту из `dispatch`, готовность находится по веткам и PR.

## Когда подходит

Два и более репозитория или роли, работа дольше одной сессии, есть PROD и риск регресса, по ходу
нужны решения владельца. Для одной правки в одном репозитории — лишние накладные расходы.
Подробности и границы применимости — в [концепции](skills/pepper-orchestrator/references/concept.ru.md).

## Состав

| Часть | Где | Переносимость |
| --- | --- | --- |
| Скилл (ядро) | `skills/pepper-orchestrator/` | любой агент, читающий файлы и запускающий Python 3 |
| CLI рабочего пространства | `skills/pepper-orchestrator/scripts/orch.py`, `safe_edit.py` | стандартная библиотека + git |
| Шаблоны (en, ru) | `skills/pepper-orchestrator/templates/` | переносимы |
| Проверка | `scripts/verification.py`, `templates/<lang>/verify-report.md` -> `reports/verify-*.md` | стандартная библиотека + git; gh для run |
| Настройки сессий | `scripts/session_settings.py`, `templates/settings/*.json` -> `orchestration/settings/*.json` | формат настроек Claude Code |
| Короткие команды | `commands/` | адаптер Claude Code |
| Агенты `orchestrator-reviewer`, `orchestrator-verifier`, `orchestrator-scout` | `agents/` | адаптер Claude Code; в других клиентах тот же бриф получает любой субагент |
| Манифест | `plugin.json` | канонический; клиентские манифесты генерируются |

Клиенты без сообщений между сессиями тоже работают: строки-указатели передаёт владелец, а `resume`
узнаёт о PR через `gh pr list`.

Самопроверка: `python3 skills/pepper-orchestrator/scripts/selftest.py`.
