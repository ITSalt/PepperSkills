# Экземпляр на РФ-VPS

Хост: `77.247.243.9` (SSH `localadmin`), новый клиентский адрес `https://lts.itsalt.ru/ru-audit`.
Существующий nginx на 443 передаёт только `/ru-audit/` на внутренний порт
`127.0.0.1:18443`; конфигурация location находится в `nginx-ru-audit.conf`.
Старый прямой TLS-вход `https://lts.itsalt.ru:8443` остаётся для v1.

## Переход 2.3.0 → 2.4.0

На VPS перед переключением сохранить копии `gateway.env`, активного
`/etc/nginx/sites-available/stands/looktwinstudio.conf`, каталога `secrets/`
и SQLite из volume `pepper-ru-audit-gateway_gateway-data`. Архив SQLite
снимать при остановленном контейнере шлюза либо через SQLite backup API;
простое копирование работающей базы не гарантирует согласованность. Проверить
ответы `/healthz` соседнего LookTwinStudio и остальных сайтов до работ.

Сначала собрать и запустить образ 2.4.0 только в Compose project шлюза:
старый вход 8443 остаётся опубликованным, новый HTTP-вход опубликован только
на `127.0.0.1:18443`. Проверить v1 `/healthz` и v2 `/v2/capabilities` через
локальный порт. Затем включить оба `location` из `nginx-ru-audit.conf` в
существующий TLS `server` для `lts.itsalt.ru` в файле LookTwinStudio,
выполнить `nginx -t` и reload. Не менять общий `location /`, другие `server`
и Certbot. Проверить публичные `/ru-audit/v2/capabilities` и
`/ru-audit/v2/diagnostic`, старый `:8443/healthz`, сайт `/healthz`, `/` и
соседние домены. Для диагностики v2 должен ответить `relay: trusted`.

При сбое вернуть сохранённый nginx-файл, проверить `nginx -t`, reload и
перезапустить Compose из `releases/2.3.0`. Не выполнять `down -v`: SQLite,
HMAC и скользящие квоты должны пережить откат. После серверной проверки
установленный клиент 2.4.0 отдельно принимается в Claude cloud/Cowork,
Codex local и Codex cloud; до этого публичный выпуск пакета не делать.

Каталог сервера `/srv/pepper-ru-audit-gateway`:

- `releases/2.4.0`, ссылка `current` — исходники и файлы поставки;
- `gateway.env` — адреса и пути без токенов;
- `secrets/` — постоянный HMAC, ключ/цепочка TLS и официальный CA Минюста;
- Docker project `pepper-ru-audit-gateway`, отдельный persistent volume
  `pepper-ru-audit-gateway_gateway-data`.

Рабочий экземпляр: 1 CPU, 512 MiB RAM, 128 PID, rootfs read-only, nftables,
UID/GID 10001 без capabilities. Квоты приложения остаются штатными: 3 запуска
за 24 часа, 1 активный на IP, 20 глобально, 32 соединения на сессию.
Сеть `10.240.81.0/24` проверяется на отсутствие пересечений перед применением.

## Управление

```sh
cd /srv/pepper-ru-audit-gateway/current
docker compose --env-file ../gateway.env -p pepper-ru-audit-gateway \
  -f compose.yaml -f deploy/compose.vps.yaml ps
# restart/up/stop применяются только к этому Compose project.
```

Не удалять production volume: он хранит скользящие квоты. Для остановки шлюза
достаточно `stop gateway` с теми же параметрами Compose. Никакие соседние
контейнеры, nginx или маршруты для этого менять не требуется.

Сертификат использует существующую lineage `/etc/letsencrypt/live/lts.itsalt.ru`.
`renew-certificate.sh` установлен как отдельный deploy hook Certbot; он действует
только для этой lineage, атомарно заменяет файлы и перезапускает только шлюз.
Это прекращает активные сетевые сессии; SQLite/HMAC сохраняются.
Продлением управляет существующий `snap.certbot.renew.timer`.

## Изолированный нагрузочный стенд

`compose.load.yaml`, `loadtool.go`, `monitor-load.py` используют отдельную внутреннюю
Docker-сеть `10.240.82.0/24`, без опубликованных портов и внешнего выхода.
Рабочая база квот не используется. В тестовом DENY_CIDRS запрещён рабочий
шлюз; адрес fixture разрешён только на изолированном стенде. На рабочем шлюзе
он включён в инфраструктурный запрет. Пер-IP лимиты тестового экземпляра подняты
до 100 для единственного генератора; остальные лимиты, native TLS, проверка
назначений, nftables и SQLite такие же, как у рабочего экземпляра.

В namespace fixture адресу loopback назначается **принадлежащий пользователю**
`82.202.140.54/32`; только в namespace тестового шлюза добавляется маршрут
`82.202.140.54/32 via 10.240.82.3`. Настоящий сервер с этим адресом трафик не
получает. Маршруты хоста не меняются. Это позволяет проверить настоящий
публичный адресный фильтр без обращения к внешним сайтам.

Генератор создаёт 20 сессий, проверяет отказ 21-й и плавно подаёт 5/10/20 × 32
TLS CONNECT. Fixture ограничен 8 KiB/s на туннель; потолок 5 MiB/s на весь тест.
Генератор удерживает полную нагрузку 20 секунд, измеряет status API и отзывает
все сессии. Монитор записывает CPU/RAM/IO, доступную память и задержки четырёх
соседних сайтов. При доступной памяти <768 MiB, ответе соседа >2 s/ошибке или
общем времени >100 s тест останавливается. У контейнеров есть отдельные CPU/RAM
лимиты. После теста удаляются **только** проект `pepper-audit-load`, его volume
и временные `load-secrets`.

Бинарник `loadtool` собирается отдельно и не входит в Git. Нагрузочный стенд
не является приёмкой реестров, браузерных сценариев или целевых VPN-клиентов.
Для v2 тот же изолированный стенд запускается с
`LOAD_CLIENT_SERVICE=client-v2 LOAD_LOG_DIR=/tmp/pepper-audit-load-v2 python3 monitor-load.py`.
Он проверяет 640 потоковых туннелей и отзыв через внутренний HTTP-вход; в
этом стенде только контейнер `client-v2` обозначен доверенным входом. Проверки
HTTPS на 443, прокси среды и CA выполняются отдельно клиентскими тестами.

Запуск на указанном VPS после сборки `loadtool`:

```sh
cd /srv/pepper-ru-audit-gateway/current/deploy
sudo sh prepare-load.sh
python3 monitor-load.py
# После сохранения /tmp/pepper-audit-load:
docker compose -p pepper-audit-load -f compose.load.yaml down -v
sudo rm -rf /srv/pepper-ru-audit-gateway/load-secrets
```

Критерии контролируемого прогона: 640 успешных туннелей, ≥4 MiB/s на полной
нагрузке, p95 установления CONNECT ≤1 s, p95 status API ≤250 ms, ноль оставшихся
туннелей после отзыва. Это проверка при искусственном ограничении потока 5 MiB/s,
а не измерение максимальной интернет-пропускной способности VPS.
