# ADR: MCP STDIO не доказывает роль вызывающей сессии

[English canonical ADR](2026-10-30-codex-stdio-bridge.md).

Продолжение: [закрытый owner STDIO и native dynamic tools](2026-10-30-codex-private-stdio-tools.md)
— новый вариант с API preflight, ещё без живой проверки изоляции. Он не отменяет
этот отказ и не означает Linux autonomy PASS.

Дата: 30 октября 2026 года. Статус: **BLOCKED / проект моста отклонён в заданной форме**.
Основание: §2 плана Linux/macOS acceptance. Привилегированный мост не поставляется.

## Что проверено фактически

Изолированные настоящие модельные вызовы CLI 0.154.0 (macOS) и 0.165.0 (Linux)
передают `params._meta.threadId`, `itemId`, `callId` и
`x-codex-turn-metadata.{thread_id,turn_id,sandbox,sandbox_mode,codex_version}`.
STDIO-процесс создан тем же native App Server, который исполняет эти треды.
Один MCP-процесс на тред, без второго resume-процесса. Это доказывает наличие
метаданных и транспорта, но не аутентификацию инициатора запроса.

Вторая проба запущена **из реального shell модуля**, workspace-write/on-request,
network_access=true (исходный тестовый профиль). Она вызвала только read-only
`context({})` другого тестового треда через поддерживаемый `mcpServer/tool/call`.
В RPC переданы `threadId` координатора и произвольный `_meta` с подставленными
itemId/callId/turnId. На macOS запрос выполнен; MCP увидел эти значения и того же
правильного native родителя. Фактический CODEX_THREAD_ID shell оставался модульным.
Это воспроизводимая подмена роли, не предположение из отсутствия документации.
Никаких scheduler/FS/shell/RPC-инструментов сам MCP не предоставляет и состояние
программы эта диагностическая проба не меняет.

Схема обоих проверенных клиентов допускает произвольный `_meta` в
`McpServerToolCallParams`. Современная
[документация MCP](https://learn.chatgpt.com/docs/extend/mcp) описывает транспорт,
но не обещает неподменяемый субъект вызова для локального STDIO.
[Исходник клиента 0.154.0](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/mcp_tool_call.rs)
добавляет native метаданные в модельном пути; это не делает другой поддерживаемый
RPC-путь недоступным и не превращает его `_meta` в удостоверение.

На Linux прежняя песочница отказывает сырому сокету (EACCES). Она скрывает PID
хоста в другом PID namespace (ENOENT для живого процесса); boot_id при этом читается.
Отказ имени процесса нельзя подменять доказательством завершения. В той же пробе
каталог служебного кода доступен только для чтения (EROFS).

## Почему предложенный мост не принят

Таблица ролей в защищённом каталоге, точный PID/start родителя, поколения, MAC или
подпись квитанций защищают последующее хранение и replay. Они не исправляют
исходную ошибку, если мост подписал операцию от имени подставленного координатора.
Фиксированная роль STDIO-процесса тоже недостаточна: сырой RPC выбирает подключение
другого треда. Наличие правильного родителя не доказывает, какой модельный shell
инициировал запрос. Самоотчёт/редактируемый JSON не становятся удостоверением.

Нельзя объявить межролевую изоляцию единого кандидата доказанной лишь потому, что
один Linux-профиль сейчас отказывает сокету. На macOS прежний профиль этот доступ
разрешает. Открывать полный RPC, отключать sandbox, включать legacy Landlock,
автоматически эскалировать или запускать второго исполнителя план запрещает.
Изменение сетевого/permission профиля либо отдельная изоляция RPC — другая граница,
которую нельзя незаметно подставить вместо проверяемой.

Дополнительно Linux branch-transition упирается в EROFS для FETCH_HEAD общего
Git-каталога worktree. Изолированный `command/exec` с той же workspaceWrite policy
повторил отказ; добавление корня `.git` и bare mirror в writableRoots его не сняло.
Setup/fetch на хост ради обхода не выполнялся. Это отдельная незакрытая приёмка
Git-подготовки, а не ошибка MCP и не основание расширить права.

## Решение и конкретная нехватка

§2 блокирует реализацию привилегированного моста и перенос scheduler на хост.
Экспериментальный код удалён из поставки. Канонический runtime сохраняет безопасный
observation_error/owner-launch; автоматические назначения Linux не заявляются.
Самостоятельно исправлен дефект cancel: unavailable не равен exited, резервирование
сохраняется. Официальные npm shims разрешаются до native binary для точного PID.

Для продолжения нужен проверенный механизм, который связывает MCP-запрос с
**аутентифицированным инициатором**, а не с выбранным RPC-полем/подключением, либо
отдельно согласованная и доказанная граница доступа к App Server. В проверенных
0.154.0/0.165.0 такого подтверждения для требуемой общей конфигурации нет. Это не
утверждение обо всех будущих версиях Codex. После появления механизма требуется
повторить контрпробу подмены и Git-подготовку, затем заново пройти §3–§7.

## Воспроизведение

```bash
python3 scripts/probe-orchestrator-codex-mcp.py --run \
  --skill plugins/pepper-orchestrator/skills/pepper-orchestrator \
  --model TEST_MODEL --output /tmp/pepper-mcp-proof.json
```

Это явный платный тест. Он изолирует CODEX_HOME, подключает только read-only MCP,
не читает внутреннюю БД Codex, не возобновляет пользовательские треды и удаляет
тестовую копию аутентификации после завершения. Свидетельство shell берётся из
точного успешного native commandExecution того же треда/хода; редактируемый файл
сверяется с ним. TypeError, таймаут или сбой самого теста не считаются PASS.
JSON verdict и обезличенные свидетельства приложены к validation-отчёту.
