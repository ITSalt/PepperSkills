## 1. Статус и назначение документа

Это самостоятельный документ передачи контекста новой сессии агента. Он объединяет
исходный запрос пользователя, уточнения пользователя, два раунда независимого ревью
и принятые поправки к плану. Читать прежнюю переписку для реализации не требуется.

На момент сохранения выполнены анализ кода, issues и документации и подготовка плана.
Реализация автономности, живые эксперименты с транспортом и новые тесты **не выполнялись**.
Issues не изменялись; расписания и новые сессии не создавались.

Пользователь попросил работать в режиме планирования, затем сохранить итоговый план.
Само наличие этого файла не означает поручения запустить реализацию, сессии или таймер.
Следующая сессия следует своему актуальному запросу пользователя.

Названия новых CLI-команд, полей и состояний ниже — проектируемые интерфейсы,
а не утверждение об их наличии в текущем плагине.

## 2. Цель и обязательный объём

Пользователь хочет убрать ручные остановки оркестратора между пакетами:

1. Использовать уже запущенные подходящие свободные сессии.
2. Периодически будить координатора для оценки прогресса, ускорения работы и запуска
   независимых пакетов параллельно.
3. Самостоятельно вызывать dispatch: пользователь больше не вводит `/dispatch`.
   При подходящей свободной сессии передавать работу туда; иначе выдавать готовую
   команду запуска нового терминала.

Пользователь **явно выбрал Claude Code и Codex CLI одновременно**. Полный автономный
цикл обоих клиентов входит в одну поставку. Ручной запасной путь при отказе транспорта
нужен, но не заменяет приёмку автономного цикла Codex.

Пример исходной проблемы: координатор сообщил, что frontend-сессия свободна и следующий
пакет — WP-FE-02, но попросил владельца вызвать dispatch. Целевое поведение: самому
проверить пакет и зависимости, назначить его подходящей сессии либо зафиксировать
конкретную причину ожидания и продолжить другую доступную работу.

Субагент предложен пользователем как способ подготовки dispatch. В итоговом плане
он используется для тяжёлых предпроверок; отдельная роль с правом менять состояние
не нужна. Окончательное назначение выполняет координатор через штатный CLI.

Поддержка обоих клиентов не означает смешанных Claude/Codex-исполнителей одной
программы или распределённой координации нескольких хостов. Существующий контракт
одного активного клиента программы сохраняется.

## 4. Факты текущей реализации, которые нужно учитывать

Все пути в этом документе указаны от корня репозитория. Базовый каталог плагина:
`plugins/pepper-orchestrator/skills/pepper-orchestrator/`.

- `references/modes/resume.md` уже содержит сверку фактов и выбор следующего действия.
  Отдельный режим `advance` не вводить: он дублировал бы эту логику.
- `references/modes/dispatch.md` предписывает передавать команду владельцу.
  `orch.py dispatch` координатору уже разрешён. Меняются и инструкции, и runtime.
- В `concept.md`, `protocol.md`, `dispatch.md` есть запрет циклического опроса.
  Его нужно согласованно уточнить для наблюдения за программой.
- Реестр `orchestration/sessions.json` содержит `sessions[wp]`; регистрации требуется
  совпадение ветки worktree с веткой пакета. Регистрация Claude уже разрешена;
  только `session read` и текущий `session send` ограничены Codex.
- `dispatch` ищет существующий worktree по ветке нового пакета. Это не механизм
  обнаружения свободной сессии предыдущего пакета.
- `streams.worktrees` считает `HEAD...base`. Это не проверка незапушенных коммитов;
  после squash merge опережение базы не доказывает несохранённую работу.
- Уже существуют `state_io.transaction`, CAS и outbox с постоянным `request-id`,
  `sending` и `outcome_unknown`. Развивать их, не создавать параллельную систему.
- `runtime_commands.state_version` учитывает документы программы, но не реестр сессий.
  Назначениям нужна собственная версия/CAS в общей транзакции.
- `session send` печатает `OWNER HANDOVER` при любом `delivered=False`, в том числе
  при неизвестном исходе. Это может спровоцировать дублирование; исправить семантику.
- Все существующие scout/reviewer/verifier-роли ограничены чтением.
- `ACCEPTED` входит в `streams.ACTIVE`, не входит в `streams.SATISFIED`; следующий
  пакет того же потока блокируется. Делегирование merge само по себе это не меняет.

## 5. Архитектура и контракты

### 5.1. Общая команда выбора действий

Добавить детерминированный `orch.py next --json`, используемый `resume`, обработчиками
событий и наблюдателем. Не дублировать правила выбора действий в отдельных режимах.

Результат содержит кандидатов на review/verify/dispatch/сверку/обращение к владельцу,
причины ожидания, необходимые проверки, отпечаток наблюдений и срок следующей проверки.
Порядок согласовать с существующим жизненным циклом программы и делегированием доставки.

- Учитывать зависимости, пути, блокировки, держателей, свободные сессии и лимит.
- Выбирать совместимую волну: несколько пакетов, допустимых по отдельности, могут
  конфликтовать друг с другом. Перед каждым назначением перепроверять условия.
- Различать обычное ожидание, недостаток данных, ошибку наблюдения и настоящий тупик.
- Отпечаток учитывает существенные внешние изменения, а не только Markdown.
  Срок проверки может наступить без изменения файлов. Текущее время само по себе
  не должно превращать каждый тик в новое событие.
- Чтение/планирование не записывает бизнес-статусы; наблюдатель не выполняет dispatch.
- Не расширять продуктовый объём и не создавать новые инициативы ради загрузки сессий.

### 5.2. Реестр сессий v2 и подключение ранее запущенных терминалов

Ключ: клиент + постоянный ID сессии. Хранить программу, модуль, worktree,
текущее назначение, историю пакетов, параметры запуска и источник их подтверждения.
Сохранить индекс `WP → session` для существующих команд.

Миграция должна сохранять прежние привязки и незавершённый outbox. Неизвестные
параметры не заполнять предположениями. Markdown остаётся источником состояния
программы, реестр — техническими данными маршрутизации, а не вторым статусом пакетов.

Имя и cwd используются для поиска кандидатов, не как достаточная идентификация.
Подключение старого терминала связывает конкретную сессию с программой, проверяет
репозиторий, ветку и отсутствие другого исполнителя. Недоступные параметры владелец
подтверждает однократно для данного экземпляра процесса; подтверждение журналируется.

Подтверждение привязать к клиенту, session ID, хосту, PID и времени запуска процесса,
worktree и отпечатку требуемой конфигурации. PID может использоваться повторно.
Если API не предоставляет нужную идентичность процесса, не выдумывать её:
зафиксировать ограничение и требовать повторной сверки при неопределённости.

Изменение процесса, cwd, settings-файла, требуемых model/effort/прав/MCP или конфигурации
программы инвалидирует совместимость и требует повторной проверки.

`claude agents --json` не доказывает model/effort/права запуска. Запись запуска доказывает
исходную, а не вечно действующую конфигурацию. Самоотчёт агента о модели — дополнительное
свидетельство, не надёжная интроспекция. Невидимая извне смена `/model` — остаточный риск,
который нужно честно описать. Не обещать полную проверяемость этих параметров.

### 5.3. Владение координатором и атомарное назначение

Один активный координатор программы. Второй может читать состояние, но не назначает работу.
В runtime хранить владельца, идентичность процесса/сессии, срок аренды и поколение владения.
Проверка владельца и поколения выполняется в транзакции каждого изменения назначения.

Истечение срока аренды само по себе не разрешает перехват: прежний координатор мог
задержаться и затем продолжить работу. Передача — после подтверждённого освобождения
или процедуры восстановления. Устаревший владелец не может записывать новые назначения.

Поколение защищает записи, но не отменяет уже отправленные сообщения. Незавершённые
отправки сверяются до создания замещающих назначений. Не освобождать ресурс/сессию
только по таймауту. Короткие state-lock не удерживать во время сети, тестов и ожиданий.

Атомарно резервировать сессию, слот параллельности, назначение и необходимые блокировки.
Версию реестра/назначения учитывать вместе с текущим CAS документов программы.

### 5.4. Структурированный dispatch и роль субагента

Добавить `dispatch --json` и `dispatch --dry-run --json`. Результаты:
заблокирован; найден кандидат на reuse; нужна новая сессия с готовой командой;
назначено; отправка ожидает подтверждения; исход неизвестен.
Dry-run сохраняет контракт отсутствия записей бизнес-состояния и назначений.

Тяжёлые предпроверки окружения, MCP и большого пакета можно делегировать субагенту,
использующему read-only-подготовку dispatch. Его вывод структурирует CLI.
Новая пишущая роль не нужна. Окончательные проверки и назначение выполняет координатор.
Простой повтор проверки и пустой тик не требуют нового субагента.

Вывод субагента не заменяет актуальную проверку условий и не разрешает обход отказа.

### 5.5. Доставка задания: общий outbox и разные транспорты

Использовать существующий outbox, расширив его контракт на оба клиента. Не смешивать
успешную постановку сообщения в очередь с подтверждённым началом исполнения.

Для Claude отправка происходит вне CLI через инструмент модели:

1. `session assign` резервирует сессию и создаёт outbox-запись с постоянным `assignment_id`.
2. Координатор вызывает `SendMessage`, включая идентификатор назначения в TASK.
3. `session sent` фиксирует результат инструмента, не объявляя пакет начавшимся.
4. Исполнитель подтверждает начало данного назначения. Только после сверки — `IN_PROGRESS`.

Сбой между отправкой и `session sent` означает неизвестный исход. Сохранять резервирование;
сначала сверить получателя, его ответ, ветку и доступные факты. Не выдавать тот же TASK
для ручной передачи и не запускать замену автоматически.

Подтверждение начала может прийти раньше `session sent`: поздняя запись отправки не
понижает состояние. Повторный TASK с тем же идентификатором не начинает вторую работу.
Не заявлять гарантию exactly-once только на основании отправительского outbox.

Для Codex использовать `codex queue` и подтверждение потребления/старта. Если необходим
App Server, проверить поддерживаемый путь без второго исполнителя того же треда.
Доказанная недоставка и неизвестный результат — разные исходы. Исправить текущий
безусловный `OWNER HANDOVER` при `delivered=False`.

### 5.6. Переиспользование worktree и гигиена контекста

Политика `session_reuse: auto | ask | never`. При включённой пользователем автономности
целевой режим — `auto` для подтверждённо совместимых сессий. Обновление плагина не должно
молча включать автономность в старых программах.

Условия reuse:

- Сессия действительно свободна; `waiting` на разрешении/ответе не равно `idle`.
- Нет другого назначения или писателя в этом worktree/ветке.
- Предыдущий пакет подтверждённо merged и обязательная работа, удерживающая сессию, завершена.
- Worktree чистый; коммиты сохранены и проверены относительно remote-ветки.
- Конфигурация и требуемые инструменты совместимы с новым пакетом.

`ACCEPTED` недостаточно даже при делегированном merge. Раннее освобождение сессии
потребует отдельной модели возврата на доработку и незавершённых веток; в первую поставку
его не включать. Это явное проектное решение, сохраняющее текущие ограничения runtime.

Squash merge и удалённую после merge ветку обрабатывать по фактам PR/принятой ревизии;
не считать `ahead > 0` относительно базы доказательством незапушенной работы.

Переход выполняет сама модульная сессия: краткая передача контекста → актуальная база →
новая ветка в своём worktree → необходимая подготовка окружения → чтение полного пакета
и применимых инструкций → подтверждение старта. Обновить раздел 0 и TASK-шаблоны.

Команда `/compact`, переданная сообщением, не считается выполненной без проверки.
Использовать доказанно поддерживаемый клиентом механизм компактизации. `/clear` не
включать в автоматический протокол без подтверждённой возможности. Если контекст
не позволяет продолжать, подготовить новую сессию. `--resume --bg` не использовать
как универсальную отправку живому Claude: возможна копия сессии.

### 5.7. Наблюдение, таймер, лимиты и пауза

Основной путь — немедленная реакция на события. Таймер страхует потерянные уведомления
и проверяет возможность продвинуть согласованный план. Начальный предлагаемый интервал
— 10 минут, настраиваемый; это проектное значение, не измеренный оптимум.

Для Claude первым проверить Monitor + `next --watch`. Наблюдатель печатает строку только
при существенном событии, доступном действии, сроке проверки или отказе наблюдения.
Проверить доступность Monitor, завершение процесса и восстановление. Cron — запасной
вариант, при котором даже пустой тик уже расходует вызов модели.

Для Codex — локальный наблюдатель с проверкой до отправки сигнала координатору.
Транспорт пробуждения зависит от успешного этапа 1. Не создавать второй координатор
при недоступности первого. Повторные сигналы объединять.

| Событие | Контракт |
|---|---|
| Включение автономности / resume | Найти либо запустить единственный наблюдатель программы. |
| Координатор занят | Объединять сигналы, не накапливать повторные задания. |
| Пауза / close | Прекратить новые пробуждения и назначения. Уже поставленный сигнал проверяет актуальное состояние перед действием. |
| Сбой наблюдателя | На resume обнаружить отсутствие процесса и восстановить наблюдение. |
| Перезагрузка машины | Первая поставка восстанавливает наблюдение на следующем resume; постоянный системный сервис не устанавливается. |
| Смена координатора | Перепривязать наблюдатель после процедуры передачи управления и сверки незавершённых операций. |

У Claude Cron срабатывает между ходами, зависит от работающей сессии и имеет ограничения
восстановления; повторяющиеся задачи по проверенной документации истекают через 7 дней.
На resume сверять ID, наличие и срок расписания, не создавать дубли. Возможности и сроки
проверить повторно для поддерживаемой версии перед реализацией.

Добавить включение/паузу автономности и `max_parallel_sessions`. Лимит учитывает активные
и зарезервированные слоты модулей, включая незавершённый dispatch; заранее определить
его семантику и не смешивать с числом одноразовых reviewer/scout-субагентов.
Конкретное числовое значение лимита в обсуждении не утверждалось; выбрать консервативное
документированное значение при реализации, не выводить его из чужих данных о хосте.

Пауза запрещает новые назначения. Остановка уже работающих исполнителей — отдельное
явное действие. Таймер не расширяет полномочия merge/deploy/PROD и не меняет sandbox.

Уведомлять о необходимом решении владельца, отказе, ожидании разрешения, подтверждённом
тупике и завершении. Обычное ожидание CI — не тупик. Повторы одинаковых уведомлений
подавлять. Пустой тик не создаёт записи в журнале и коммита.

Во всех инструкциях закрепить: периодическая сверка файлов/Git/PR/CI/сессий разрешена;
бессодержательные сообщения исполнителям «как дела?» не отправляются. Вопрос сессии
возникает по конкретному признаку, например устаревшей блокировке или противоречию фактов.

### 5.8. Что остаётся за пределами обязательной первой поставки

- Автоматическое создание новых сессий. Первая поставка переиспользует подходящую
  существующую сессию либо выдаёт готовую команду нового терминала.
- Для последующего автозапуска предусмотреть отдельную возможность
  `session_launch: owner | orchestrator`, по умолчанию `owner`, с явным делегированием,
  проверенным CLI запуска, сохранением выбранных ограничений и регистрацией фактического ID.
  Наличие этого пункта не разрешает запускать новые сессии с расширенными правами.
- On-demand-блокировки общих путей (#23): отдельно разрешить противоречие между ранним
  освобождением в старом triage и текущим правилом удержания общих файлов до интеграции.
- Ранний reuse после ACCEPTED, смешанные клиенты одной программы, координация разных
  хостов и постоянный системный сервис наблюдения.

## 6. Этапы реализации и условия перехода

### Этап 1. Проверка транспорта обоих клиентов

В одноразовой программе проверить: сообщение свободной сессии запускает работу без
человека; busy/waiting не принимаются за свободное состояние; подтверждение начала
доступно; повтор не создаёт второго исполнителя; путь компактизации проверен.
Для Claude проверить Monitor и резервный Cron, для Codex — queue и при необходимости
App Server. Зафиксировать версии, реальные результаты и ограничения.

**Условие приёмки:** если Codex нельзя пробудить без второго исполнителя, автономный
цикл Codex не принят. Общее ядро можно продолжать разрабатывать, но поставку для обоих
клиентов нельзя объявить готовой или молча заменить ручным путём.

### Этап 2. Реестр v2, миграция, подключение терминалов

Реализовать привязки и подтверждения процесса, индекс WP, историю, совместимость,
сохранение незавершённого outbox. Миграция не делает неизвестные сессии доверенными.

### Этап 3. Владение координатором и надёжные назначения

Реализовать поколение владельца, CAS реестра, резервирование слотов и протокол
assign/send/sent/started. Исправить ручную передачу при неизвестном исходе.
Проверить аварийное восстановление до включения автоматического dispatch.

### Этап 4. next, структурированный dispatch, reuse

Добавить единый выбор действий, совместимые волны и диагностику ожидания.
Подключить подготовку через субагента там, где она оправдана. Реализовать переход
сессии на следующий пакет, проверки Git и политику контекста.

### Этап 5. Наблюдение и инструкции

Подключить оба адаптера пробуждения, лимиты, паузу, дедупликацию, восстановление,
уведомления. Согласованно обновить Claude/Codex-инструкции, концепцию, протокол,
resume/dispatch, шаблоны пакетов и документацию. Сохранить общее каноническое ядро
и существующий способ сборки Codex-ресурсов.

### Этап 6. Проверки и живая приёмка

Добавить содержательные регрессии в существующие selftest/runtime/reliability-наборы,
пройти необходимые проверки репозитория и упаковку. Проверить извлечённые артефакты,
а не только исходники. Затем пройти живые сценарии отдельно в каждом клиенте.
Нативные проверки заявляемых платформ, включая Windows/PowerShell, отделять от
локальных проверок macOS/Linux. Не объявлять непроверенную платформу поддержанной
на основании одного локального теста.

## 7. Матрица приёмки

| Сценарий | Требуемый результат |
|---|---|
| Подключение ранее запущенного терминала | Конкретная сессия доступна для reuse после подтверждения недостающих параметров. |
| Два пакета подряд | Та же сессия, новая ветка, без пользовательского /dispatch. |
| Независимые пакеты | Параллельное исполнение в пределах лимита и без конфликтов выбранной волны. |
| Снятие зависимости/блокировки | Пакет подхватывается автоматически; до этого показана точная причина ожидания. |
| Потерянный READY | Наблюдение обнаруживает факты и продолжает программу. |
| ACCEPTED без merge | Следующий пакет того же потока не получает сессию преждевременно. |
| Squash merge / удалённая remote-ветка | Сохранность работы определяется корректно, не по одному ahead относительно базы. |
| Грязный worktree / несовместимость / waiting | Новый пакет сессии не назначается. |
| Лимит параллельности | Резервируемые назначения учитываются; лимит не превышается конкурентными вызовами. |
| Двойной сигнал | Одно назначение и один исполнитель. |
| Сбой между SendMessage и session sent | Неизвестный исход сохраняется; нет слепого повтора и OWNER HANDOVER. |
| Подтверждение старта раньше session sent | Поздняя запись отправки не понижает состояние. |
| Перезапуск старого терминала / повторное использование PID | Прежнее подтверждение не переносится молча на другой процесс. |
| Два координатора / возврат устаревшего владельца | Второй не назначает при действующем владельце; старое поколение не пишет после передачи. |
| Сбой во время смены ветки/подготовки | Повтор сверяет фактическую ветку и назначение, не создаёт ветку или задачу заново вслепую. |
| Сбой/перезапуск наблюдателя | Восстановление без дубля таймера и без второго координатора. |
| Пауза после постановки сигнала | Обработка сигнала не запускает новую работу. |
| Пустой тик | Нет уведомления, записи в журнале и коммита; для Monitor/watch проверяется отсутствие пустого вызова модели. |
| Наступивший срок при неизменных файлах | Проверка не теряется из-за одинакового отпечатка документов. |
| Ошибка наблюдения | Не выглядит нормальной тишиной; диагностируется. |
| Контекст требует обновления | Проверенная компактизация либо подготовка новой сессии. |
| Ограничения полномочий | Автономность не расширяет merge/deploy/PROD, доступ к БД и sandbox. |

Автоматические тесты с подменой транспорта не заменяют живые сценарии двух клиентов.
Записывать наблюдавшиеся проверки отдельно от непроведённых.

## 10. Начало работы в новой сессии

1. Прочитать этот файл и актуальные применимые инструкции репозитория.
2. Проверить текущий запрос пользователя: продолжение планирования или реализация.
3. Проверить рабочее дерево и актуальный main, сохранить чужие изменения; выбрать базу
   с учётом того, что документ мог быть сохранён в отстающей ветке.
4. При поручении реализации начать с этапа 1, не с создания таймера в рабочей программе.
5. Не переспрашивать уже решённое: оба клиента, автоматический dispatch и reuse — цель.
   Новые развилки обосновывать конкретным результатом проверки, а не повторять вопросы аудита.
6. Вести отчёт с версиями, выполненными проверками, ограничениями и оставшейся работой.
