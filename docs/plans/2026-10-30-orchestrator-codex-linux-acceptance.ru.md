# Pepper Orchestrator: Codex на Linux и повторная приёмка macOS

Дата: 30 октября 2026 года. Статус: этапы 1–2 исследованы; обязательный gate §2 — BLOCKED. См. ADR `../adr/2026-10-30-codex-stdio-bridge.ru.md` и отчёт `../validation/pepper-orchestrator-0.13.1-linux-gate.ru.md`. Привилегированный мост не поставляется; выполнены независимое исправление безопасной отмены и диагностические проверки.

## Цель и исходная точка

Устранить блокировку автономности Codex на Linux при действующей песочнице и
повторить сквозную приёмку на Linux и macOS после изменений общего ядра.
Claude сохраняет работающий транспорт и все прежние гарантии.

Проверенная база: `origin/main`, `e1134fdf92346a2911163042b74d8a47b7831b46`,
тег `pepper-orchestrator-v0.13.0` указывает на этот же коммит. Локальная ветка при
подготовке плана оставалась на `abd7016`; реализацию начинать от актуального main,
а не продолжать старый снимок Codex-части. План подготовлен по релизному коду
через `git show origin/main:...`; ветка не переключалась.

По релизному отчёту: Linux / Codex CLI 0.165.0 / workspace-write отказал безопасно
из-за доступа к App Server и `/proc`. Живой macOS-прогон относился к предыдущему
снимку общего ядра. В этой подготовке живые прогоны не повторялись; локальный CLI
определён как 0.154.0. Доступность конкретных возможностей проверять на каждой
машине, не выводить из современной документации поддержку старой версии.

Архивы 0.13.0 неизменяемы. Сначала воспроизвести их поведение, затем исправлять
код и собирать новый кандидат (предварительно 0.13.1). Успех кандидата нельзя
приписывать прежнему архиву 0.13.0. Публичный выпуск в этот план не входит.

## 1. Воспроизвести и локализовать отказ

В отдельной тестовой программе на Linux проверить архив из релиза, предварительно
сверив SHA256SUMS. Записать ОС/ядро, Python, все пути Codex в PATH, фактически
запущенный native binary и его версию, App Server, профиль sandbox/approvals,
доступную модель, схему RPC и выбранный endpoint. Секреты не включать в отчёт.

Отдельно выполнить из процесса владельца и из реального shell-вызова координатора
и модуля: наблюдение того же App Server, queue, получение идентичности процесса,
`next`, проверку владельца, transition. Сохранить errno и вызываемый слой.
Различить запрет сокета, сетевой namespace, скрытый PID namespace, недоступный
boot_id и ошибку прав чтения. Проверить явный App Server и shared proxy.

Аналогично повторить исходный архив на macOS: это обновит приёмку собственно
0.13.0 и отделит последствия общего ядра от Linux-ограничения.

Критерий этапа: минимальный воспроизводимый отказ и список всех зависимых путей,
включая `owner`, `compatible`, `transition`, cancel, запуск/восстановление watcher
и compaction. Одной успешной проверки сокета недостаточно.

## 2. Доказать безопасный способ взаимодействия

Основной проектный вариант — узкий локальный мост через поддерживаемый Codex
MCP STDIO. Он работает в контексте локального хоста, где доступны процессы и
App Server; shell координатора и модулей сохраняет прежнюю песочницу.
Это новая явно подключаемая возможность инструмента, а не расширение shell-прав.

До изменения общего ядра сделать короткий изолированный прототип и проверить:

- MCP действительно доступен из реальных сессий нужного CLI при прежнем профиле;
- соединение относится к исходному runtime, без второго исполнителя того же треда;
- доступные штатные метаданные позволяют надёжно привязать вызов к сессии/роли;
  переданный моделью thread ID сам по себе не является аутентификацией;
- мост не требует доступа shell к сокету App Server или host `/proc`;
- подключение к уже работающей сессии поддержано клиентом либо требует явного
  переподключения владельцем с последующим повторным attach/claim;
- матрица возможностей 0.154.0 и 0.165.0 проверена фактически; при необходимости
  минимальная поддерживаемая версия повышается с понятной диагностикой;
- подключение не превращается в общий доступ к JSON-RPC, shell или файловой системе.

После прототипа зафиксировать ADR с точным механизмом привязки вызывающей сессии,
разрешёнными операциями, размещением доверенного кода и восстановлением.
Не обещать безопасность механизма только на основании наличия MCP.
Если нужную привязку и узкие полномочия доказать нельзя, этап блокирует
реализацию: сохранить безопасный отказ и описать конкретную нехватку API.
Не заменять результат отключением sandbox, legacy Landlock, выдачей полного
доступа к App Server, автоматической эскалацией или вторым resume-процессом.

## 3. Провести границу между наблюдением и исполнением

Основные места: `autonomy.py`, `codex_transport.py`, `codex_adapter.py`,
`runtime_commands.py`, генерация нативной конфигурации, новый модуль моста.
Сохранить единый алгоритм назначения и существующие CLI-контракты; MCP вызывает
те же операции ядра, не реализует второй scheduler.

- На стороне хоста: наблюдение разрешённых сессий/процессов, детерминированные
  операции координатора с CAS, проверенный queue в зарегистрированный модуль,
  наблюдение старта и compaction уже загруженного idle runtime.
- У координатора: выбор действий по `next`, dispatch, reconcile и consume через
  ограниченный интерфейс, привязанный к программе и поколению владения.
- У модуля: смена ветки, fetch и worktree_setup выполняются его shell в прежней
  песочнице. Мост не запускает setup или другой код проекта на стороне хоста.
- Для transition: свежая проверка сессии/процесса через мост и техническая
  квитанция, привязанные к assignment, worktree, конфигурации и поколению.
  Транспорт квитанции и защита от повторного использования фиксируются в ADR.
- Служебный код/конфигурация моста не должны изменяться исполнителем и затем
  исполняться за пределами его песочницы. Не загружать произвольный Python из
  изменяемого worktree и не принимать произвольные CLI-команды или пути.
- Модулям недоступны операции координатора и чужие сессии. Запросы не могут
  менять sandbox, approvals, модель, MCP, выполнять merge/deploy/PROD или создавать
  новые терминалы/исполнителей. Инструменты, меняющие состояние, не помечать read-only.
- Наблюдения собираются вне короткой транзакции, затем проверяются версия/CAS,
  поколение и актуальность. Переходы паузы, close и recover проверяются заново.
- Нет доверия к редактируемому JSON-снимку, подставленному PID/ID или времени файла.
  Для переноса наблюдений предусмотреть целостность, срок и защиту от replay.

Watcher остаётся локальным процессом наблюдения: не назначает работу и не вызывает
модель на пустом тике. Его lifecycle связан с программой; без systemd/launchd.
Подтверждения PID/endpoint не переносятся между машинами или перезапусками.

## 4. Уточнить состояния отказа и восстановление

Ввести различие «процесс жив», «процесс доказанно завершён» и «наблюдение
недоступно». В релизном cancel исключение process_identity сейчас превращается
в `still_live=False`; запрет чтения не должен становиться доказательством остановки.
Покрыть это отдельной регрессией, сохранив остальные проверки отмены.

При потере моста/App Server, изменении процесса/конфигурации или устаревшем
наблюдении новые назначения блокируются. Существующие assignment, outbox, слоты
и блокировки сохраняются. `outcome_unknown` не разрешает повтор или handover.
После рестарта — явная проверка runtime и resume/recover, сверка незавершённых
отправок, затем продолжение того же назначения. Истечение lease недостаточно.

Отключение моста возвращает понятную диагностику и owner-launch без объявления
автономности готовой. Не понижать режим до опроса модели по таймеру.

## 5. Регрессии и упаковка

Расширить `autonomy_selftest.py`, native smoke и тест извлечённых архивов:

| Сценарий | Ожидаемый результат |
|---|---|
| Shell не видит App Server и host `/proc`, мост доступен | `next`/dispatch/transition работают через разрешённую границу |
| PID существует, но чтение запрещено | Нельзя отменить назначение как остановленное |
| Чужая сессия/программа/роль, старое поколение, replay | Отказ без изменения резервирования |
| Подмена служебного кода, пути или конфигурации | Нет исполнения на хосте; требуется восстановление владельцем |
| Перезапуск моста/App Server, повтор PID, потеря соединения | Инвалидирование доверия и сверка outbox до продолжения |
| Сбой после queue, ранний STARTED, повтор TASK | Одно назначение, без второго исполнителя |
| Пауза/close после сигнала, возобновление watcher | Нет новых назначений после паузы, один восстановленный watcher |
| Пустой тик и неизменные факты | Нет модели, журнала, коммита и лишней записи состояния |
| Dirty/waiting/config drift/ACCEPTED без merge | Reuse запрещён |
| Native config изменён новым base, setup неизвестен | Подготовка владельцем/явное восстановление, без слепого повтора |

Прогнать все прежние selftest/runtime/reliability/autonomy, включая 15 Claude
регрессий и дополнительные тесты, `scripts/check.sh`, native transport smoke,
проверки извлечённых skill/plugin ZIP и встроенной Codex-копии, CI Linux/macOS/
нативный Windows/PowerShell и сверку воспроизводимости архивов.
Одинаковый общий runtime во всех поставках; инструкция установки моста и
минимальные версии входят в упаковку. На Windows полный живой цикл не заявляется.

## 6. Сквозная приёмка единого кандидата на Linux и macOS

Расширить `scripts/test-orchestrator-autonomy-live.py`. На обеих машинах использовать
архив одного и того же коммита кандидата с одинаковым SHA256, настоящий CLI,
App Server, координатор и два исполнителя в отдельных worktree. Отдельно сохранять
версии/профили каждого хоста. Основной Linux-профиль — workspace-write/on-request
с прежними ограничениями; тестовая сеть и runtime roots описываются явно.

Драйвер действует только как владелец одноразового приватного GitHub-репозитория:
подготавливает сессии/мост, проверяет факты, выполняет разрешённые тестовые PR/merge.
Он не делает dispatch/reconcile вместо координатора и не исполняет setup вместо модуля.
Платные прогоны остаются явными, в обычный CI не добавляются.

| Критерий | Доказательство |
|---|---|
| Два независимых WP параллельно | Перекрывающиеся окна фактических ходов, а не только две резервации |
| Следующий WP в прежней сессии после merge | Тот же thread/worktree, новая ветка; squash merge и удалённая remote-ветка |
| Автоматическое продолжение | Сигнал watcher → consume → dispatch координатора без пользовательского `/dispatch` |
| Потерянное уведомление / снятая зависимость | Самостоятельное обнаружение и продолжение без ручного толчка |
| Пауза после постановки сигнала | Consume не даёт права назначить работу; после resume сверяется текущее состояние |
| Перезапуск watcher и моста | Одно восстановленное наблюдение, незавершённая отправка не повторяется |
| Waiting / запрос разрешения | Сессия занята; подтверждение владельца требуется по прежним правилам |
| Компактизация | Завершённый contextCompaction event в том же runtime |
| Сохранение песочницы | Отрицательные пробы прямого доступа shell и запрещённых операций по-прежнему отказывают |
| Пустое наблюдение | Счётчики/события показывают отсутствие пустых вызовов модели |

Для обоих архивов сохранить JSON verdict, обезличенные события, коммит, SHA256,
команды запуска, результаты и ограничения. После теста остановить только созданные
процессы, архивировать тестовые сессии и репозитории, сохранить журналы.

Если изменения общего ядра затронут Claude-пути, повторить его Linux live-сценарий
из того же кандидата; 15 регрессий обязательны независимо от этого.

## 7. Завершение и границы

Обновить `references/autonomy.md`, Codex workflow, resume/dispatch/close, EN/RU
шаблоны, CHANGELOG и отдельный отчёт с матрицей исходной 0.13.0 и кандидата.
Указать новые локальные возможности MCP и способ их подключения/отключения.
Не удалять историческую запись о Linux-отказе исходного релиза.

Работа завершена только при PASS кандидата из одного архива на Linux и macOS,
зелёных обязательных проверках и сохранённых ограничениях sandbox/approvals.
При нехватке штатного API результат — конкретный блокер и воспроизводимый тест,
а не заявление о готовой автономности. Изменения предоставить через отдельную
ветку `codex/` и PR с доказательствами; публикацию нового релиза не выполнять
без отдельного запроса владельца.

Вне работы: #23, ранний reuse после ACCEPTED, смешанные клиенты, несколько хостов,
постоянный системный сервис, автосоздание сессий, пользовательские PROD/БД и deploy.

## Проверенные источники

- Релизный код и отчёт: `e1134fd`, `docs/validation/pepper-orchestrator-0.13.0.md`.
- [Официальные границы permissions](https://learn.chatgpt.com/docs/permissions#what-profiles-control):
  MCP имеет собственные средства контроля; разрешение локальных сокетов/localhost
  само по себе открывает доступ к локальному сервису.
- [Linux enforcement](https://learn.chatgpt.com/docs/permissions#how-enforcement-works):
  bubblewrap/seccomp; legacy Landlock не является решением изоляции App Server.
- [MCP в Codex](https://learn.chatgpt.com/docs/extend/mcp): STDIO и конфигурация,
  ограничения списка инструментов. Поддержку полей в старых CLI проверять отдельно.
- [App Server](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread):
  текущие RPC/история/сессии; документация не доказывает наличие этих возможностей
  в 0.154.0/0.165.0 и не гарантирует аутентификацию вызывающего MCP-инструмент треда.
