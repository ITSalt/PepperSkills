## Цель и исходная точка

Устранить блокировку автономности Codex на Linux при действующей песочнице и
повторить сквозную приёмку на Linux и macOS после изменений общего ядра.
Claude сохраняет работающий транспорт и все прежние гарантии.

Проверенная база: `origin/main`, `e1134fdf92346a2911163042b74d8a47b7831b46`,
тег `pepper-orchestrator-v0.13.0` указывает на этот же коммит. Продолжение вести
в существующей ветке `codex/orchestrator-linux-acceptance`, draft PR #42, поверх
безопасного исправления `6d59bfa` и отчёта `35b3626`; проверить актуальный HEAD/main.
Не возвращаться к старому `abd7016` и не терять проверенное исправление.

По релизному отчёту: Linux / Codex CLI 0.165.0 / workspace-write отказал безопасно
из-за доступа к App Server и `/proc`. Живой macOS-прогон относился к предыдущему
снимку общего ядра. В §1 исходный архив уже повторно проверен: macOS PASS,
Linux WAIT / безопасный отказ. Эти результаты остаются историей 0.13.0.
Локальный CLI — 0.154.0; Linux-факты предыдущего прогона — 0.165.0.
Доступность возможностей проверять на каждой машине. Новый закрытый канал
на Linux ещё не проверен; документация не доказывает поддержку старой версии.

Архивы 0.13.0 неизменяемы. Сначала воспроизвести их поведение, затем исправлять
код и собирать новый кандидат (предварительно 0.13.1). Успех кандидата нельзя
приписывать прежнему архиву 0.13.0. Публичный выпуск в этот план не входит.

## 1. Воспроизвести и локализовать отказ

Этап выполнен в предыдущем отчёте; повторять исходный архив только при изменении
окружения или недостаточном доказательстве, а не заново для продолжения плана.

В отдельной тестовой программе на Linux проверить архив из релиза, предварительно
сверив SHA256SUMS. Записать ОС/ядро, Python, все пути Codex в PATH, фактически
запущенный native binary и его версию, App Server, профиль sandbox/approvals,
доступную модель, схему RPC и выбранный endpoint. Секреты не включать в отчёт.

Отдельно выполнить из процесса владельца и из реального shell-вызова координатора
и модуля: наблюдение того же App Server, queue, получение идентичности процесса,
`next`, проверку владельца, transition. Сохранить errno и вызываемый слой.
Различить запрет сокета, сетевой namespace, скрытый PID namespace, недоступный
boot_id и ошибку прав чтения. Проверить явный App Server и shared proxy.

Аналогично повторить исходный архив на macOS: это обновит приёмку собственно
0.13.0 и отделит последствия общего ядра от Linux-ограничения.

Критерий этапа: минимальный воспроизводимый отказ и список всех зависимых путей,
включая `owner`, `compatible`, `transition`, cancel, запуск/восстановление watcher
и compaction. Одной успешной проверки сокета недостаточно.

## 2. Доказать безопасный способ взаимодействия

### 2.1. Сохранить отказ от MCP metadata как доказательства роли

Реальный macOS shell модуля подменил `_meta` на соединении координатора через
`mcpServer/tool/call`. PID родителя, таблица ролей и подпись квитанции не исправляют
исходную подмену субъекта. Прежний ADR и запрет привилегированного MCP-моста
сохраняются. Запрет Linux-сокета сам по себе не доказывает общую безопасность.

### 2.2. Новый основной вариант: private App Server STDIO + dynamic tools

Владелец явно запускает один native App Server с `--listen stdio://` и держит
анонимные stdin/stdout pipes. У этого runtime нет Unix/TCP listener, shared proxy,
remote control или файлового RPC inbox. Отсутствие альтернативного ingress
проверяется фактически. Shell не получает нового доступа к App Server или `/proc`.

Узкие инструменты регистрируются через экспериментальный `dynamicTools` на
`thread/start`. Владелец получает server request `item/tool/call`; роль определяется
по защищённой регистрации полученного thread ID и нативному envelope
`threadId`/`turnId`, а не по аргументам модели. Запрос сопоставляется с текущим
`item/started`, активным ходом, известным инструментом и epoch канала.
Повтор, неизвестная сессия или старое поколение отказывают без записи состояния.
Call ID — ключ дедупликации, не секрет и не доказательство роли.

Так исчезает доступный модели управляющий endpoint, позволявший выбирать чужое
MCP-соединение. Если модель получит pipes или другой ingress, вариант также
небезопасен. Dynamic tools сами по себе не являются аутентификацией.
Точная модель угроз и требования к реализации — в новом ADR.

Локальный preflight без модели: CLI 0.154 принимает experimental initialize,
ephemeral thread с dynamic tool и workspace-write/on-request; клиентский
`item/tool/call` отвергается. Схема `--experimental` содержит dynamicTools у start,
но не у resume. Это только доступность API: реальные вызовы, изоляция FD,
исходный network=true и persisted-tool resume ещё требуют проверки.

### 2.3. Живой gate на Linux, затем macOS

Сначала только read-only `pepper_context({})`, без scheduler и записи состояния.
Проверить реального координатора и модуль при прежних эффективных правах,
включая тестовый network=true. Сохранить схему, native binary/хэш, конфигурацию,
нативные события и errno. Требуются следующие доказательства:

- Обычные вызовы обоих тредов имеют правильные разные envelope и роли.
- Подмена thread/turn/role в arguments не меняет субъекта. Валидная операция
  координатора от модуля отказывает в общем dispatcher до side effects.
  Одного `additionalProperties:false` недостаточно для проверки авторизации.
- Нет owner RPC через socket, proxy/queue, remote ingress, stdin, унаследованные
  FD, `/proc`, `/dev/fd`, ptrace/pidfd. Пробы касаются только созданных процессов.
  Невидимый PID в одном namespace не заменяет всю проверку доступа.
- Модель не может изменить host-код, роли, конфигурацию, epoch и restart inputs.
  Проверить symlink/path/import injection. Не исполнять Python из worktree или
  общей writable temp-директории; `chmod 0600` не изолирует того же пользователя,
  читаемый токен в файле/env не является защищённой capability.
- Native approval остаётся pending без решения человека. Инструмент и watcher
  не могут принять запрос, изменить permissions или добавить allow-rules.
- Disconnect/restart инвалидирует epoch. После доказанной остановки старого
  runtime проверяются persisted tools, тот же thread ID и outbox. Новый тред
  не считается recovery прежнего; второй resume-исполнитель запрещён.

Для каждого теста PASS/FAIL/INCONCLUSIVE. Timeout, ошибка Python или writable JSON
не доказывают изоляцию: нужны события владельца и точный commandExecution.
Смена профиля ради успеха инвалидирует прогон. Необходимую минимальную версию
определить фактическими прогонами 0.154/0.165. Если API отсутствует — unsupported
и безопасный отказ. Только полный gate разрешает этап 3; сам preflight его не снимает.

### 2.4. Независимый gate Git preparation

Из shell модуля отдельно проверить fetch, ветку и worktree_setup. В прежнем Linux
FETCH_HEAD был EROFS даже с дополнительными roots: workspace-write защищает `.git`
и resolved gitdir рекурсивно. Нельзя обходить это переносом gitdir, mount-трюком,
host fetch/setup, legacy Landlock или расширением профиля.

Если CLI требует approval, сохранить WAIT и точный штатный запрос. Решение
принимает человек; план не разрешает автоодобрение, session grant или allow-rules.
Записать дельту прав и решение. Прогон с более широкими правами не закрывает gate
исходного неизменённого профиля. Без допустимого пути оставить
BLOCKED_GIT_PREPARATION даже после security PASS; это ещё не Linux autonomy PASS.

### 2.5. Выбранный тестовый профиль: песочница с явными Git-разрешениями

Владелец выбрал `Git-approved` для одноразового Linux-fixture. Ограниченный
native grant и реальная Git-подготовка теперь PASS; evidence по ссылке выше.
Исторический неизменённый профиль остаётся BLOCKED_GIT_PREPARATION. Production-
профиль и глобальные config не менялись; выбор не разрешает grants другой программе. В финальном disposable прогоне отдельно выбранный
владельцем контроллер применяет только ограниченное решение для точных шести
roots на один turn. Он фиксирует WAIT и 0 ручных native UI кликов; это не выдаётся
за ручное подтверждение каждого запроса. В production owner_main grant ручной.

Сохранить workspace-write/on-request и закрытый канал владельца. Проверен native
механизм `request_permissions_tool=true` в изолированном config с grant шести
Git-каталогов на один ход. При интеграции записывать точные requested/resolved
paths, команду, срок grant и решение владельца. Предпочитать command/turn scope; постоянный session grant требует
отдельного явного выбора владельца. Без общего allow-rule на `git`, автоодобрения,
полного доступа к home/root, общего host runner и запуска setup на хосте.
Если CLI не умеет ограниченный grant — указать предел; не заменять его молча
исполнением без песочницы.

Fetch, создание ветки и setup по-прежнему выполняются через native command path
модуля. До решения человека сохранять WAIT. С действующим grant повторить
отрицательные пробы записи owner-кода/состояния и доступа к RPC/FD; другая сессия,
программа или перезапущенный runtime не должны наследовать разрешение.
Одобренный scope учитывать в защищённом состоянии владельца, сверять drift
конфигурации/прав перед продолжением назначения. Restart не даёт права повторно
выдать grant или повторить работу с неизвестным результатом.

После успешного живого цикла указывать `PASS (Git-approved, on-request)`, дельту
прав и число действий владельца. Это автономная координация со штатными паузами
на approval; не обещание работы без подтверждений и не PASS прежнего профиля.
Gate привязки роли и изоляции RPC остаётся обязательным. Полностью доверенный
режим без песочницы — другой явный выбор, предпочтительно в отдельной одноразовой
среде; этим предложением он не включается.

Конечный helper завершился до конца хода. Истечение прав у новых команд не
доказывает отзыв launch permissions уже работающего фонового terminal. Перед
production reuse проверять завершение подготовки и активные terminals/processes.
Git metadata с grant изменяема: host-наблюдения должны закреплять common dir/пути,
исключать project hooks/filters и не исполнять setup на хосте.

Основание API: [native approvals](https://learn.chatgpt.com/docs/app-server#command-execution-approvals),
исходники 0.165 `request_permissions` и policy merging из English-плана.
Наличие API не доказывает, что grant на конкретный protected gitdir сработает:
нужны настоящий запрос, решение и проверка исполнения ограничений.

## 3. Провести границу между наблюдением и исполнением

Основные места: `autonomy.py`, `codex_transport.py`, `codex_adapter.py`,
`runtime_commands.py`, owner launcher и обработчик dynamic tools.
Сохранить единый алгоритм и CLI-контракты; handler вызывает то же ядро, а не второй
scheduler. В транспорте нужен один multiplexed reader, сериализованная запись и
отдельная маршрутизация ответов/server requests/approvals. Не вызывать вложенное
синхронное ожидание RPC из callback и не держать lock на время RPC или модели.

- На стороне хоста: наблюдение разрешённых сессий/процессов, детерминированные
  операции координатора с CAS, проверенный queue в зарегистрированный модуль,
  наблюдение старта и compaction уже загруженного idle runtime.
- У координатора: выбор действий по `next`, dispatch, reconcile и consume через
  ограниченный интерфейс, привязанный к программе и поколению владения.
- У модуля: смена ветки, fetch и worktree_setup выполняются его shell в прежней
  песочнице. Мост не запускает setup или другой код проекта на стороне хоста.
- Для transition: свежая проверка сессии/процесса через мост и техническая
  квитанция, привязанные к assignment, worktree, конфигурации и поколению.
  Транспорт квитанции и защита от повторного использования фиксируются в ADR.
- Служебный код/конфигурация моста не должны изменяться исполнителем и затем
  исполняться за пределами его песочницы. Не загружать произвольный Python из
  изменяемого worktree и не принимать произвольные CLI-команды или пути.
- Модулям недоступны операции координатора и чужие сессии. Запросы не могут
  менять sandbox, approvals, модель, MCP, выполнять merge/deploy/PROD или создавать
  новые терминалы/исполнителей. Инструменты, меняющие состояние, не помечать read-only.
- Наблюдения собираются вне короткой транзакции, затем проверяются версия/CAS,
  поколение и актуальность. Переходы паузы, close и recover проверяются заново.
- Нет доверия к редактируемому JSON-снимку, подставленному PID/ID или времени файла.
  Для переноса наблюдений предусмотреть целостность, срок и защиту от replay.

Watcher остаётся локальным наблюдателем: использует owner client без нового
управляющего endpoint, не назначает работу и не вызывает модель на пустом тике.
Его lifecycle связан с программой; без systemd/launchd.
Подтверждения PID/endpoint не переносятся между машинами или перезапусками.

## 4. Уточнить состояния отказа и восстановление

В кандидате уже введено различие «процесс жив», «доказанно завершён» и «наблюдение
недоступно» с отдельной регрессией. В исходном релизном cancel исключение
process_identity превращалось в `still_live=False`. Сохранить исправление:
запрет чтения не доказывает остановку; остальные проверки отмены обязательны.

При потере моста/App Server, изменении процесса/конфигурации или устаревшем
наблюдении новые назначения блокируются. Существующие assignment, outbox, слоты
и блокировки сохраняются. `outcome_unknown` не разрешает повтор или handover.
После рестарта — явная проверка runtime и resume/recover, сверка незавершённых
отправок, затем продолжение того же назначения. Истечение lease недостаточно.

Отключение моста возвращает понятную диагностику и owner-launch без объявления
автономности готовой. Не понижать режим до опроса модели по таймеру.

## 5. Регрессии и упаковка

Расширить `autonomy_selftest.py`, native smoke и тест извлечённых архивов:

| Сценарий | Ожидаемый результат |
|---|---|
| Shell не видит App Server и host `/proc`, мост доступен | `next`/dispatch/transition работают через разрешённую границу |
| PID существует, но чтение запрещено | Нельзя отменить назначение как остановленное |
| Чужая сессия/программа/роль, старое поколение, replay | Отказ без изменения резервирования |
| Подмена служебного кода, пути или конфигурации | Нет исполнения на хосте; требуется восстановление владельцем |
| Перезапуск моста/App Server, повтор PID, потеря соединения | Инвалидирование доверия и сверка outbox до продолжения |
| Сбой после queue, ранний STARTED, повтор TASK | Одно назначение, без второго исполнителя |
| Пауза/close после сигнала, возобновление watcher | Нет новых назначений после паузы, один восстановленный watcher |
| Пустой тик и неизменные факты | Нет модели, журнала, коммита и лишней записи состояния |
| Dirty/waiting/config drift/ACCEPTED без merge | Reuse запрещён |
| Native config изменён новым base, setup неизвестен | Подготовка владельцем/явное восстановление, без слепого повтора |

Прогнать все прежние selftest/runtime/reliability/autonomy, включая 15 Claude
регрессий и дополнительные тесты, `scripts/check.sh`, native transport smoke,
проверки извлечённых skill/plugin ZIP и встроенной Codex-копии, CI Linux/macOS/
нативный Windows/PowerShell и сверку воспроизводимости архивов.
Одинаковый общий runtime во всех поставках; инструкция owner-launch и
минимальные версии входят в упаковку. На Windows полный живой цикл не заявляется.

## 6. Сквозная приёмка единого кандидата на Linux и macOS

Расширить `scripts/test-orchestrator-autonomy-live.py`. На обеих машинах использовать
архив одного и того же коммита кандидата с одинаковым SHA256, настоящий CLI,
App Server, координатор и два исполнителя в отдельных worktree. Отдельно сохранять
версии/профили каждого хоста. Основной Linux-профиль — workspace-write/on-request
с прежними ограничениями; тестовая сеть и runtime roots описываются явно.

Драйвер действует только как владелец одноразового приватного GitHub-репозитория:
подготавливает сессии/мост, проверяет факты, выполняет разрешённые тестовые PR/merge.
Он не делает dispatch/reconcile вместо координатора и не исполняет setup вместо модуля.
Платные прогоны остаются явными, в обычный CI не добавляются.

| Критерий | Доказательство |
|---|---|
| Два независимых WP параллельно | Перекрывающиеся окна фактических ходов, а не только две резервации |
| Следующий WP в прежней сессии после merge | Тот же thread/worktree, новая ветка; squash merge и удалённая remote-ветка |
| Автоматическое продолжение | Сигнал watcher → consume → dispatch координатора без пользовательского `/dispatch` |
| Потерянное уведомление / снятая зависимость | Самостоятельное обнаружение и продолжение без ручного толчка |
| Пауза после постановки сигнала | Consume не даёт права назначить работу; после resume сверяется текущее состояние |
| Перезапуск watcher и моста | Одно восстановленное наблюдение, незавершённая отправка не повторяется |
| Waiting / запрос разрешения | Сессия занята; подтверждение владельца требуется по прежним правилам |
| Компактизация | Завершённый contextCompaction event в том же runtime |
| Сохранение песочницы | Отрицательные пробы прямого доступа shell и запрещённых операций по-прежнему отказывают |
| Пустое наблюдение | Счётчики/события показывают отсутствие пустых вызовов модели |

Для обоих архивов сохранить JSON verdict, обезличенные события, коммит, SHA256,
команды запуска, результаты и ограничения. После теста остановить только созданные
процессы, архивировать тестовые сессии и репозитории, сохранить журналы.

Если изменения общего ядра затронут Claude-пути, повторить его Linux live-сценарий
из того же кандидата; 15 регрессий обязательны независимо от этого.
