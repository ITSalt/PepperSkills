# Структура PepperSkills: предложение и план миграции

> **Историческое предложение, заменено итоговым решением.** Вариант с `shared`
> и брендовыми каталогами отклонён. Действующая структура — `plugins/<name>/`;
> обоснование и состояние этапов см. в [итоговом отчёте](repository-structure-2026-09-26.ru.md).
> Ниже сохранён первоначальный текст и его статус на момент составления.

Дата проверки: 26 сентября 2026. Статус: **проект структуры, перенос не выполнен**.
Аудит относится к текущей рабочей копии, включая незакоммиченные изменения.

## Решение

Сохранить порядок **название → бренд → формат → ОС, если нужна → интерфейс,
если нужен**. Добавить `shared` для общего содержимого. Редактируемый исходник
каждого скилла существует один раз; брендовые каталоги содержат только реальные
отличия. Устанавливаемые пакеты собираются отдельно.

Три разных пространства:

| Пространство | Назначение | Кто изменяет |
| --- | --- | --- |
| `<name>/` | Исходники, документация и настройки вариантов | Автор |
| `dist/` | Самодостаточные каталоги, архивы, готовые чат-промпты и marketplace | Сборщик |
| `~/.agents/skills/`, каталоги клиентов | Установка на машине пользователя | Выбранный установщик или пользователь |

«Без дублирования» означает отсутствие нескольких редактируемых реализаций.
Копии внутри независимых релизных пакетов необходимы: пакет должен работать
после скачивания на другую машину без доступа к исходному репозиторию.

## Что обнаружено сейчас

- Три настоящих `SKILL.md`, все в `plugins/<name>/skills/<name>/`.
- Семь исправных переходных симлинков в корневых `pepper-*`:
  три `anthropic`, два `openai`, два файла чат-промпта.
- Шесть архивов: три `.skill` в корневых папках и три `.plugin.zip` внутри
  `plugins/`. Первые отслеживаются Git, вторые исключены через `.gitignore`.
- Корневые README скиллов — переходные указатели; основные README находятся
  внутри `plugins/`. Это два входа в один материал, а не две реализации скилла.
- SHA-256 подтвердил одинаковые копии LICENSE в трёх плагинах и корне,
  одинаковые Claude/Cursor-манифесты для каждого плагина, одинаковые
  Claude/Cursor marketplace. Два CHANGELOG также совпадают байт в байт;
  это повод проверить содержание, а не автоматически объединять истории.
- Chat-адаптеры и клиентские манифесты уже генерируются, но лежат рядом с
  редактируемыми источниками. Пути жёстко зашиты в сборщики и проверки.
- `.github/PULL_REQUEST_TEMPLATE.md` ещё требует обновлять варианты
  `anthropic/` и `openai/`; шаблон issue предлагает старый путь.
- `Claude outputs/`, `_to_delete/`, `.DS_Store`, `__pycache__` — локальные
  материалы или служебные файлы. Первые два уже игнорируются Git. Они не
  являются источниками релиза и не удаляются в рамках этого предложения.

Именно сосуществование старой и новой навигации создаёт большую часть «каши».
Незавершённый перенос уже виден в `git status`; его нельзя заменять откатом
или строить миграцию только из закоммиченного HEAD.

## Предлагаемое дерево

Ниже полная модель на примере одного продукта. Каталоги вариантов создаются
только при наличии отличий; это не требование создать все показанные ветви.

```text
PepperSkills/
├── README.md
├── README.ru.md
├── LICENSE
├── CONTRIBUTING.md
├── SECURITY.md
├── CODE_OF_CONDUCT.md
├── pepper-prompt-engineer/
│   ├── README.md
│   ├── README.ru.md
│   ├── CHANGELOG.md
│   ├── package.json                    # метаданные PepperSkills, не npm
│   ├── shared/
│   │   ├── skill/
│   │   │   └── pepper-prompt-engineer/ # устанавливаемый корень скилла
│   │   │       ├── SKILL.md
│   │   │       ├── references/
│   │   │       ├── scripts/
│   │   │       ├── examples/
│   │   │       └── assets/             # только если нужны
│   │   ├── chat/
│   │   │   └── prompt.template.md      # общий шаблон, не готовая копия
│   │   └── assets/                     # общие материалы оформления пакета
│   ├── openai/
│   │   ├── plugin/
│   │   │   ├── overlay.json            # только OpenAI-поля
│   │   │   └── submission/             # только если есть материалы подачи
│   │   └── chat/
│   │       └── overlay.md              # только специфичный текст, если нужен
│   ├── anthropic/
│   │   └── plugin/
│   │       └── overlay.json            # только отличия, если нужны
│   ├── cursor/
│   │   └── plugin/
│   │       └── overlay.json            # только отличия, если нужны
│   └── tests/
│       └── evals/
├── pepper-creative-mode/               # те же правила
├── pepper-ru-web-compliance/           # те же правила + NOTICE.md
├── scripts/                            # общие сборщики, проверка, установка
│   └── schemas/                        # внешние схемы и схема package.json
├── docs/
│   ├── repository-structure.ru.md
│   ├── installation-and-updates.ru.md
│   ├── releases/                       # прежние RELEASE-NOTES-*.md
│   ├── history/                        # завершённые аудиты и отчёты
│   └── qa/                             # подтверждения приёмки
├── .github/                            # CI и шаблоны
└── dist/                               # генерируется, игнорируется Git
```

Повтор `<name>` внутри `shared/skill/` — техническая граница пакета, а не
дубликат контента. По спецификации поле `name` должно совпадать с именем
каталога, содержащего `SKILL.md`. Путь `shared/skill/SKILL.md` нарушил бы это
правило для имени `pepper-prompt-engineer`. Избранная структура позволяет
подключить исходник симлинком без промежуточной сборки.
[Спецификация Agent Skills](https://agentskills.io/specification).

Если такая вложенность окажется слишком тяжёлой, более короткая альтернатива —
`skills/<name>/SKILL.md` и `packages/<name>/<brand>/<format>/`. Она удобнее для
инструментов, но разделяет один продукт между двумя корнями. Для текущего
запроса рекомендуется дерево выше: один видимый каталог на продукт.

## Однозначные правила

1. `shared` — нейтральная ветвь, а не бренд. Бренды называем `openai`,
   `anthropic`, `cursor`, `google`. Название модели не создаёт новую ветвь.
2. Форматы: `skill`, `plugin`, `chat`. Marketplace — каталог пакетов,
   а не четвёртый вариант реализации скилла. MCP, hooks и commands — компоненты
   плагина; добавляются только при реальной необходимости.
3. `package.json` — один внутренний рецепт продукта с собственным `$schema`.
   В нём хранятся имя, версия пакета, общие издательские поля, путь источника,
   перечень поддерживаемых целей, требования и статус проверки каждой цели.
   Это новый предлагаемый контракт, а не существующий CLI или npm-пакет.
   Версия протокола остаётся в `SKILL.md`; одинаковые поля не вводим вручную дважды.
4. Если бренд использует общий скилл без изменений, достаточно записи цели
   в рецепте. Не создаём `openai/skill` с копией или README «смотри shared».
   Если требуется `agents/openai.yaml`, его источник хранится в
   `openai/skill/`, а сборщик помещает его в стандартный путь внутри пакета.
5. Рецепт явно перечисляет overlays. Порядок применения: shared → бренд/формат
   → ОС → интерфейс. Необъявленная замена файла или повтор поля — ошибка сборки.
   Массивы заменяются целиком; не используем неявное «умное слияние».
6. Общие инструкции и методика редактируются только в shared. Chat-шаблон
   включает блоки оттуда. В overlay допускается только обоснованное отличие:
   например, ручной режим без запуска Python. Проверка выявляет ручные копии
   основных разделов. Специфичные evals подтверждают отличающееся поведение.
7. `macos/`, `windows/`, `linux/` появляются только при разных файлах,
   командах или зависимостях. При различии лишь команды установки используем
   раздел инструкции, а не копию скилла. Сейчас необходимость трёх реализаций
   каждого скилла не установлена.
8. `cli/`, `desktop/`, `web/`, `api/` — необязательный последний уровень.
   Без различий по ОС допустим `openai/plugin/desktop/`; с различиями —
   `openai/plugin/windows/desktop/`. Не добавляем пустые `all/` или `common/`.
   Конкретный продукт (`codex`, `chatgpt`, `claude-code`, `cowork`) и его
   возможности записываются в цели: один ярлык `desktop` этого не объясняет.
9. В исходном дереве нет готовых `.skill`, `.zip`, сгенерированных чат-текстов,
   клиентских манифестов и симлинков, имитирующих отдельные версии продукта.
10. Один LICENSE в корне; сборщик вкладывает его в пакеты. NOTICE скилла
    сохраняется отдельно. Человеческий README — на уровне продукта;
    краткий INSTALL для поставки генерируется при необходимости.
11. Evals и тестовые fixtures находятся в `<name>/tests/`, кроме скриптов
    диагностики, которые нужны самому пользователю: они остаются внутри skill.
    Исторические QA-артефакты не переписываются под новые пути задним числом.

## Сборка и распространение

```text
shared/skill/<name> + package.json + объявленные overlays
  ├─ dist/<name>/shared/skill/<name>/...
  ├─ dist/<name>/openai/plugin/<name>/...
  ├─ dist/<name>/anthropic/plugin/<name>/...
  ├─ dist/<name>/cursor/plugin/<name>/...
  └─ dist/<name>/shared/chat/prompt.md
```

Каждый plugin-каталог содержит реальные `skills/<name>/...` и подходящий
манифест. OpenAI поддерживает переносимый корневой `plugin.json`;
`.codex-plugin/plugin.json` нужен лишь для выбранной совместимости. Для
Claude и Cursor сборщик делает их манифесты. Не поддерживаем эти файлы вручную.
[OpenAI: упаковка](https://developers.openai.com/plugins/build/plugins),
[Claude: манифест](https://code.claude.com/docs/en/plugins-reference),
[Cursor: манифест](https://prod.cursor.com/docs/reference/plugins).

Архивы лежат рядом с собранными каталогами в `dist/<name>/<brand>/<format>/`.
Имя включает продукт, версию и отличающийся target. `.skill` сохраняется только
для подтверждённых потребителей; для загрузки custom skill в Claude публикуем
документированный `.zip`. Не предполагаем поддержку любого расширения любым UI.
[Claude: упаковка custom skills](https://support.claude.com/en/articles/12512198-how-to-create-custom-skills).

Обычный пользователь получает готовые файлы через Releases. Git marketplace
требует отдельно решённой доставки: **игнорируемый dist не появится у пользователя
после clone**. Рекомендуется генерируемая ветка `distribution` этого же репозитория:

```text
distribution (только результат CI)
├── .agents/plugins/marketplace.json
├── .claude-plugin/marketplace.json
├── .cursor-plugin/marketplace.json
├── packages/<name>/<brand>/plugin/<name>/...
└── provenance.json
```

Каждый marketplace указывает на реальные самодостаточные каталоги своей
платформы внутри этой ветки. На source-ветке скрытые marketplace убираются после
переключения установочных инструкций. Если клиент не умеет выбирать Git ref,
та же сборка публикуется в отдельный distribution-репозиторий; это проверяется
до отключения старого канала. Публикация в этой работе не производится.

`provenance.json` фиксирует commit исходников, версию сборщика, цели и SHA-256.
Архивы не имеют ссылок наружу. Временные файлы и snapshots реестров не попадают
в выпуск. Независимые сборки одного входа должны давать одинаковые байты.

Для Skills CLI используется **прямой путь к каноническому skill**, а не
предположение, что произвольная вложенность обнаружится автоматически.
Root discovery также проверяется отдельно: обход CLI зависит от стандартных
контейнеров и найденных manifest-файлов.
[Vercel Skills: discovery](https://github.com/vercel-labs/skills#skill-discovery).

## Карта переноса

В таблице `<name>` означает каждый из трёх существующих продуктов.

| Сейчас | После миграции |
| --- | --- |
| `plugins/<name>/skills/<name>/` | `<name>/shared/skill/<name>/` |
| `plugins/<name>/README*`, `CHANGELOG.md` | `<name>/README*`, `CHANGELOG.md` |
| `plugins/<name>/plugin.json` | Общие поля → `<name>/package.json`; OpenAI-поля → `<name>/openai/plugin/overlay.json` |
| `plugins/<name>/.{codex,claude,cursor}-plugin/` | Генерируются только в пакетах |
| `plugins/<name>/adapters/chat/*.template.md` | `<name>/shared/chat/` |
| `plugins/<name>/adapters/chat/` готовые тексты | `dist/<name>/shared/chat/` либо брендовая цель при реальных отличиях |
| `plugins/pepper-ru-web-compliance/submission/` | Документы подачи → `pepper-ru-web-compliance/openai/plugin/submission/`; fixtures и проверки → `tests/submission/` |
| `plugins/pepper-ru-web-compliance/submission-tests.json` | `pepper-ru-web-compliance/tests/submission/` |
| `plugins/<name>/assets/` | `<name>/shared/assets/`, кроме действительно брендовых материалов |
| Две копии NOTICE compliance | Один `pepper-ru-web-compliance/NOTICE.md` после сравнения содержания |
| `<name>/*.skill`, `plugins/<name>/*.plugin.zip` | `dist/` и release assets |
| Семь переходных симлинков | Удаляются после обновления потребителей |
| Корневые `.agents/plugins`, `.claude-plugin`, `.cursor-plugin` | Генерируемые каталоги ветки distribution |
| `RELEASE-NOTES-*.md` | `docs/releases/` |
| `docs/modernization-*.ru.md` | `docs/history/` с обновлением ссылок |

## Порядок миграции

1. Сохранить полный текущий working tree, включая untracked `plugins/`,
   в отдельном локальном снимке/ветке. Зафиксировать хэши источников и ссылки.
   Git stash без untracked или checkout из HEAD для этого недостаточны.
2. Перенести реальные исходники, сохранить имена скиллов и относительные
   ссылки внутри пакета. Evals переносить вместе с обновлением их путей.
3. Ввести схему рецепта и общий resolver путей. Перевести на него
   `build-skills.sh`, `build-plugins.sh`, `sync-plugin-manifests.py`,
   оба chat-сборщика, `check.sh`, `test-packages.py`. Убрать проверку,
   завязанную на «ровно шесть архивов»: список определяется рецептами.
4. Обновить README, CONTRIBUTING, INSTALL, submission-документы,
   deep-dive и `.github`-шаблоны. Убрать требование вручную синхронизировать
   две брендовые реализации. Старые опубликованные URL перечислить отдельно;
   временные текстовые указатели допустимы только со сроком удаления.
5. Собрать dist и distribution-каталог во временном месте. Проверить все
   marketplace пути до переключения. Обновить ручные пользовательские симлинки
   через явную карту old → new; чужие файлы и plugin caches не перезаписывать.
6. Пройти проверки ниже. Удалить переходные aliases и прежний `plugins/`
   только после переноса всех содержательных файлов. Переключать опубликованный
   канал отдельным релизным действием, не выдавая локальную сборку за публикацию.

## Критерии завершения

- В source-ветке ровно три канонических `SKILL.md`; у каждого один владелец пути.
- Все поддерживаемые цели объявлены в рецептах, неизвестные сочетания дают
  ошибку, а не молчаливый fallback на другой клиент.
- Нет битых относительных ссылок, старых путей в действующих инструкциях и
  ручных редакций сгенерированных файлов. Исторические отчёты исключены.
- ZIP проходит распаковку отдельно от репозитория; нет symlinks, path traversal,
  вложенных архивов, bytecode и локальных данных. LICENSE/NOTICE сохранены.
- Содержимое базового skill в каждой поставке совпадает с источником по хэшам;
  все намеренные отличия перечислены. Сборка воспроизводима и не меняет sources.
- Существующие selftest, eval checks и submission-тесты проходят после переноса.
- Установка → вызов → обновление → отключение проверены отдельно в заявленных
  клиентах; версии клиентов, ОС и результаты записаны. ZIP-проверка этого не заменяет.
- Отдельно проверены установка по прямому пути через Skills CLI, общий каталог
  с симлинками и отсутствие двойного обнаружения plugin + standalone skill.
- macOS, Windows/WSL, Linux отмечаются `tested`, `documented` или `unsupported`.
  Нельзя превращать прочитанную документацию в заявление о пройденном тесте.

Обзор актуальных схем и команды для **нынешних** путей:
[Установка и обновление](../installation-and-updates.ru.md).
