> Материал-источник для написания статьи. Это не статья, а структурированный
> технический разбор: что делает скилл, на каких механиках построен, какие
> ноу-хау использует и почему каждое решение валидно (со ссылками на
> исследования и документацию). Везде, где это важно, отдельно помечено, что
> является **доказанным исследованием**, что — **рекомендацией вендора**, а что
> — **инженерным решением автора скилла**.

## 1. Краткая суть (TL;DR)

`pepper-prompt-engineer` — это **скилл-агент, который не выполняет задачу
пользователя, а собирает за него production-ready промпт** для выполнения этой
задачи другой моделью (или другой сессией). Пользователь описывает задачу
свободным текстом — на выходе получает структурированный промпт, отформатированный
под конкретную целевую модель (Claude / ChatGPT / Gemini / DeepSeek / Universal),
готовый к копированию одним кликом.

Ключевая идея: **промпт-инжиниринг — это воспроизводимый инженерный процесс, а не
искусство**. Скилл кодифицирует рабочий процесс senior prompt engineer в детерминированный
конвейер: классификация задачи → анализ полноты → сборка по фиксированному
шаблону из 10 блоков → условное подключение модулей → полировка под модель →
самопроверка по чек-листу.

Главное архитектурное разграничение, на котором держится весь скилл:

> **Скилл строит промпт, а НЕ исполняет задачу.** Если пользователь пишет
> «напиши парсер на Python» — скилл выдаёт *промпт для написания парсера*, а не код.

Поставляется в двух формах из одной методологии:
- **chat-промпт** — один системный промпт, вставляется в любой чат-интерфейс;
- **Claude Code skill** — полный пакет с references, примерами, валидатором и evals.

## 2. Какую проблему решает

Промпты «на коленке» систематически страдают пятью дефектами. Скилл устраняет
каждый адресно:

| Дефект ad-hoc промпта | Чем оборачивается | Как закрывает скилл |
|---|---|---|
| Недоформулированные критерии успеха («сделай хорошо») | Модель не знает, что считать готовым результатом; вывод размытый | Обязательный блок `SUCCESS_CRITERIA` из 3–5 **измеримых** критериев + запрет на расплывчатые формулировки |
| Игнор форматирования под целевую модель | Промпт под Claude в XML работает хуже на Gemini и наоборот | Детекция `target_model` + полировка синтаксиса под каждую модель |
| Пропуск служебных модулей | Факт-чекинг, исполнение кода, разнообразие, мультимодальность теряются | 4 условных модуля A/B/C/D с автодетекцией по триггерам |
| Галлюцинации при нехватке данных | Модель выдумывает факты вместо вопроса | Обязательное «правило неопределённости» (uncertainty rule) в блоке `CONSTRAINTS` |
| Отсутствие самопроверки | Модель не сверяется с требованиями перед ответом | Обязательный блок `VERIFICATION` — чек-лист-стоп-гейт для исполняющей модели |

Концептуально: скилл превращает **неявные знания** опытного промпт-инженера
(какую роль дать, какой тон, какую длину, когда нужны few-shot-примеры, как
форматировать под Claude vs GPT) в **явный, документированный и проверяемый**
артефакт.

## 3. Архитектура и режимы поставки

### 3.1 Два режима — одна методология

| Режим | Что это | Когда брать |
|---|---|---|
| **Универсальный chat-промпт** (`chat-prompt.md`) | Один самодостаточный системный промпт (~800 строк), вставляется первым сообщением в Claude.ai / ChatGPT / Gemini / DeepSeek | Минимальное трение: одна вставка, работает в любом чат-UI |
| **Claude Code skill** (`anthropic/SKILL.md` + references) | Полноценный скилл с подгружаемыми по требованию справочниками, примерами, Python-валидатором, evals | Повторяемое использование внутри Claude Code |

Обе формы реализуют идентичную методологию CRAFT+. Разница — в упаковке и в том,
как раскрывается контекст.

### 3.2 Progressive disclosure (трёхуровневая загрузка контекста)

Версия для Claude Code построена на принципе **прогрессивного раскрытия** из
спецификации Anthropic Agent Skills — контекст подгружается только когда нужен,
чтобы не раздувать окно модели:

- **Tier 1 — YAML-фронтматтер** (`name` + `description`): всегда в контексте. Именно
  `description` с триггер-фразами определяет, активируется ли скилл вообще.
- **Tier 2 — тело `SKILL.md`** (~236 строк): загружается при активации. Содержит
  весь рабочий процесс и ссылки на детали.
- **Tier 3 — `references/`, `examples/`, `scripts/`**: подгружаются по необходимости,
  когда конкретный шаг требует деталей (например, точные правила форматирования
  под Gemini читаются только если выбран Gemini).

Структура пакета (23 файла):

```
pepper-prompt-engineer/
├── SKILL.md                  # Tier 2 — точка входа, весь workflow
├── INSTALL.md                # инструкция установки
├── references/               # Tier 3 — 7 справочников
│   ├── methodology.md        # CRAFT+: 10 блоков детально
│   ├── conditional-modules.md# модули A/B/C/D + двуязычные триггеры
│   ├── target-models.md      # форматирование под 5 моделей
│   ├── question-strategy.md  # стратегия вопросов
│   ├── scope-check.md        # детекция мега-задач
│   ├── security.md           # anti-injection
│   └── output-format.md      # Markdown-шаблоны + JSON-схема
├── examples/                 # Tier 3 — 6 эталонных выходов
├── scripts/validate.py       # программный валидатор (16 + до 2 условных)
├── scripts/run_evals.py      # схема-чек и run sheet для evals
└── evals/evals.json          # 10 регрессионных тест-кейсов
```

**Почему это важно для статьи:** скилл — не «один большой промпт», а
структурированная система знаний с управляемой подгрузкой. Это и есть разница
между «промпт-шаблоном» и «инженерным скиллом».

## 4. Ядро методологии: CRAFT+ и его 10 блоков

### 4.1 Что такое «CRAFT+»

Классический **CRAFT** — это community-фреймворк промпт-инжиниринга (Context,
Role, Action, Format и вариации). Он стоит в одном ряду с **CO-STAR** (Sheila Teo,
победитель GovTech Singapore GPT-4 Prompt Engineering Competition, 2023) и
**RISEN** (Kyle Balmer). Все три — практические схемы, которые заставляют модель
учитывать отдельные слои задачи (контекст, роль, формат, ограничения) вместо того,
чтобы схлопывать их в один.

«**+**» в CRAFT+ — это расширение классики практиками 2025–2026 годов:
- измеримые критерии успеха (`SUCCESS_CRITERIA`),
- явные ограничения и анти-галлюцинационное правило (`CONSTRAINTS`),
- условные модули (факт-чекинг / код / разнообразие / мультимодальность),
- блок самопроверки (`VERIFICATION`),
- полировка под целевую модель.

Любой выходной промпт **всегда** состоит из этих 10 семантических блоков (порядок
фиксирован; пропускать можно только два — см. ниже).

### 4.2 10 блоков: что, зачем, на чём основано

| # | Блок | Что задаёт | Зачем (обоснование) |
|---|------|-----------|---------------------|
| 1 | **ROLE** | Роль + уровень экспертизы + аудитория вывода | Ролевое позиционирование задаёт «поведенческое рулевое управление»; «You are a helpful assistant» не управляет ничем. Идёт из CO-STAR/RISEN (Role) |
| 2 | **TASK** | Что сделать — одно императивное предложение | Одна задача на промпт; устраняет размытость deliverable |
| 3 | **CONTEXT** | Фон, входные данные, домен | **Анти-паттерн:** не пересказывать запрос пользователя агенту, а описать суть задачи для исполняющей модели |
| 4 | **SUCCESS_CRITERIA** | 3–5 **измеримых** критериев готовности | Правило: если критерий нельзя проверить программно (тестом) — он слишком расплывчатый, переписать |
| 5 | **ACTIONS** | Нумерованные шаги | *Пропускается* для простых атомарных задач |
| 6 | **CONSTRAINTS** | Что НЕ делать + scope + **uncertainty rule** | Содержит обязательное анти-галлюцинационное правило (см. 6.5) и разрешение конфликтов по приоритетам |
| 7 | **REASONING_MODE** | Как модели думать: Direct / CoT / ToT / ReAct / Self-Consistency | Выбирается под тип задачи; для frontier-моделей CoT **не вставляется** (см. 6.4) |
| 8 | **OUTPUT_FORMAT** | Точная структура, длина, тон, формат | Литеральный шаблон вместо «в чистом виде»; длина в символах/словах/буллетах, а не «коротко» |
| 9 | **EXAMPLES** | 1–3 few-shot-примера | *Пропускается*, если формат полностью задан; максимум 3 (см. 6.3 про деградацию контекста) |
| 10 | **VERIFICATION** | 3–5 пунктов самопроверки для исполняющей модели | Чек-лист как стоп-гейт перед выводом, зеркалит `SUCCESS_CRITERIA` |

**Правило пропуска блоков:** удалять можно только `ACTIONS` (для простых задач) и
`EXAMPLES` (когда формат однозначен). Остальные 8 блоков обязательны всегда —
минимально заполненный блок допустим, удалённый — нет.

## 5. Конвейер обработки запроса (10 шагов)

При активации скилл прогоняет запрос через детерминированный конвейер. Это
сердце «инженерности» — каждый запрос проходит одни и те же ворота.

```
Шаг 0a. Проверка контекста разговора
        └─ новая задача / ответы на уточнения / доработка прошлого промпта
Шаг 0b. Режим: generate (с нуля) или improve (улучшить существующий промпт)
Шаг 0c. Детекция целевой модели (явно указана? иначе — спросить)
Шаг 1.  Классификация задачи
        ├─ тип: reasoning / creative / technical / analysis / conversation / data
        ├─ сложность: simple / moderate / complex
        └─ домен: code / marketing / analytics / content / other
Шаг 1.5 Scope check — детекция мега-задачи (несколько подсистем / размытый scope)
Шаг 2.  Анализ полноты + стратегия вопросов
        └─ критичный пробел → вопрос; некритичный → решение + запись в assumptions
Шаг 3.  РАЗВИЛКА
        ├─ есть критичные пробелы / модель не определена → выдать уточнения и СТОП
        └─ иначе → собирать промпт
Шаг 4.  Выбор reasoning mode (Direct / CoT / ToT / ReAct / Self-Consistency)
Шаг 4.5 Детекция условных модулей (A/B/C/D по двуязычным триггерам)
Шаг 5.  Сборка 10 блоков CRAFT+ + активные модули (язык вывода — английский)
Шаг 6.  Языковая обёртка (первая строка промпта — инструкция языка ответа)
Шаг 7.  Полировка под целевую модель (XML / Markdown / гибрид)
Шаг 8.  Самопроверка по чек-листу (опц. — прогон validate.py)
Шаг 9.  Сборка вывода (code-блок + секции на языке пользователя)
```

Две «развилки», где скилл может остановиться и не отдавать промпт:
- **Шаг 1.5** — если задача похожа на мега-проект, скилл предупреждает и
  предлагает 3 варианта (MVP / разбить / собрать как есть) вместо заведомо
  поверхностного результата.
- **Шаг 3** — если не хватает критичной информации (или не определена модель),
  скилл задаёт ≤3 уточняющих вопроса с вариантами-подсказками и останавливается.

## 6. Ключевые механики и ноу-хау

### 6.1 Полировка под целевую модель (model-specific formatting)

Один и тот же набор 10 семантических блоков получает **разный синтаксический
скелет** в зависимости от целевой модели. Это основано на официальной документации
вендоров.

| Аспект | Claude | ChatGPT (GPT) | Gemini | DeepSeek | Universal |
|---|---|---|---|---|---|
| Обёртка блоков | XML-теги `<role>…` | Markdown `# Role` **плюс** XML вокруг единиц контента | Markdown `## Role` | XML или Markdown | XML-скелет + Markdown внутри |
| Управление рассуждением | `effort` / режим расширенного мышления | `reasoning_effort` | `thinking_level` | thinking effort low/high/max | что даёт интерфейс |
| Эмфаза | Мягкая на директивах про инструменты | Стандартная | Прямая, декларативная | Стандартная | Мягкая |
| Триггер CoT | Никогда | Никогда | Никогда | Никогда | Никогда |
| Давление по длине | Opus 5 отвечает длинно — просить кратко явно | Стандартное | Резать сильнее всех | Стандартное | Резать |
| Разделители | Закрывающие XML-теги | Markdown-отступы | `---` между секциями | Любые | Закрывающие XML |
| Таблицы | Внутри XML | Внутри `#`-секций | Нативно | Любые | Внутри XML |

Конкретные ноу-хау форматирования:
- **Claude:** каждый блок в XML-тегах (прямая рекомендация документации Anthropic).
  Избегать эскалированной эмфазы вида «CRITICAL: YOU MUST» — но **только** на
  директивах, управляющих вызовом инструментов и скиллов: именно эту область
  оговаривает вендор, и именно там современные модели перетриггеривают. Обычные
  `NEVER` / `MUST` в правилах форматирования допустимы — Anthropic сама их использует
  в своих примерах промптов. Prefill не применять: с моделей 4.6 он не поддерживается
  и возвращает 400.
- **GPT:** Markdown-заголовки для иерархии **плюс** XML-теги вокруг единиц контента —
  так рекомендует сам гайд OpenAI, приводя кейс Cursor: структурированные XML-спеки
  подняли следование инструкциям. Для длинных и агентных промптов — секция
  `# Persistence` с формулировкой вендора. Никакой цифры прироста гайд к ней не
  привязывает; ранняя версия скилла приписывала ей «+20%», это удалено.
- **Gemini:** декларативный стиль, таблицы для сравнений, `---` между секциями,
  явное `Goal:` в начале. Плюс два требования из Gemini 3 Developer Guide: держать
  температуру на дефолтной 1.0 (снижение ведёт к зацикливанию и деградации) и писать
  **коротко** — модель лаконичнее предшественниц, а многословный промпт-инжиниринг
  провоцирует over-analysis. Из пяти целей эту режем сильнее всего.
- **DeepSeek:** обычный CRAFT+ без специфичных приёмов. Идентификаторы —
  `deepseek-v4-pro` и `deepseek-v4-flash`; `deepseek-chat` и `deepseek-reasoner`
  выведены из обращения 24 июля 2026. Прежнее правило «единственная цель, где полезна
  явная вставка CoT» вместе с ними и ушло: у V4 есть собственные уровни thinking.
- **Universal:** компромиссный гибрид (XML-скелет + Markdown), минимально-рисковые
  решения — работает приемлемо на всех, но неоптимально для каждой конкретной.

**Сквозная механика поверх всех целей — управление глубиной размышления.** Все четыре
вендора дают пользователю ручку глубины рассуждения (`effort`, `reasoning_effort`,
`thinking_level`, thinking effort у V4). Она живёт **вне текста промпта**, поэтому
попадает не в промпт, а в секцию «⚙️ Настройки перед использованием» — по строке в
каждом готовом ответе. Обратная сторона того же правила: «think step by step» в промпт
не вставляется ни для одной цели, потому что конкурирует с этой ручкой.

### 6.2 Условные модули A/B/C/D

Сверх базовых 10 блоков скилл по триггерам подключает до четырёх модулей. Каждый
модуль имеет **двуязычные (RU+EN) триггеры**, встраиваемый блок (на английском,
вставляется перед `OUTPUT_FORMAT`) и инструкции пользователю под каждую модель.

| Модуль | Триггеры (примеры) | Что встраивает | Зачем |
|---|---|---|---|
| **A. Факт-чекинг** | даты, имена, статистика, цены, «сейчас/сегодня/актуально», research/news/legal/medical | `<fact_checking>`: проверять каждый факт веб-поиском; без поиска — не выдумывать, выдать дисклеймер; помечать `[UNVERIFIED]` | Борьба с галлюцинациями на фактических утверждениях |
| **B. Исполнение кода** | вычисления/агрегации >5 операций, CSV/JSON/Excel, финмодели, «посчитай/обработай датасет» | `<computation_strategy>`: использовать code execution для ВСЕХ расчётов; иначе — выдать самодостаточный Python-скрипт для Colab | Обоснование: воспроизводимость и проверяемость результата, масштаб данных за пределами одного ответа, отсутствие накопления ошибки в длинных цепочках зависимых шагов. Числовой оценки ошибки модуль не содержит — см. §10 |
| **C. SSoT (протокол креативности)** | N>1 вариантов одного типа, «удиви/нестандартно/разные», случайный выбор, стохастические симуляции | `<creativity_protocol>`: сначала сгенерировать случайную строку как источник энтропии, затем детерминированно вывести вариант | Обход «mode collapse» от RLHF на задачах, требующих реального разнообразия (см. 6.3) |
| **D. Мультимодальный ввод** | приложенные изображения/PDF/файлы, «опиши картинку/извлеки текст из PDF» | `<multimodal_input>`: явно ссылаться на каждый файл, цитировать дословно перед анализом, указывать страницы | Дисциплина работы с не-текстовым вводом, борьба с «придумыванием» невидимого |

**Порядок вставки** строго задан (мультимодальность → факт-чекинг → вычисления →
креативность): каждый следующий модуль опирается на контекст предыдущего.
Несколько модулей могут сработать одновременно (например, research-задача с
расчётами активирует A и B).

«**NOT a trigger**» прописаны явно, чтобы избежать ложных срабатываний: например,
единичная операция («2+2», «5 кг в фунты») **не** активирует модуль кода, а одна
творческая задача без запроса множественности **не** активирует SSoT.

### 6.3 SSoT — главное research-based ноу-хау

Это самая нетривиальная и доказательно обоснованная механика скилла.

**Проблема.** После RLHF-дообучения модели склонны к *mode collapse*: на запрос
«придумай 10 вариантов» они выдают близкие, статистически вырожденные ответы и не
умеют воспроизводить заданное распределение вероятностей (например, «выбери A с
вероятностью 70%, B — 30%» при многократном запуске даёт перекошенную статистику).

**Решение SSoT (String Seed of Thought).** Модель сначала генерирует случайную
строку (источник энтропии), а затем **детерминированно** выводит из неё вариант:
- равномерный выбор из N: `result = sum(ord(c) for c in string) mod N`;
- взвешенное распределение: rolling hash → попадание в интервал, пропорциональный
  весам;
- творческая композиция: разбить строку на сегменты, по каждому выбрать компонент
  (сеттинг/тон/персонаж/твист) из списка-кандидата.

Ключевое требование протокола: **новая строка для каждого независимого решения** —
переиспользование строк разрушает статистическую независимость.

**Источник:** Misaki & Akiba, «String Seed of Thought: Prompting LLMs for
Distribution-Faithful and Diverse Generation», [arXiv:2510.21150](https://arxiv.org/abs/2510.21150)
(подана 24.10.2025, на рассмотрении ICLR). Работа вводит понятие *Probabilistic
Instruction Following* (PIF) и показывает, что инъекция энтропии через случайную
строку улучшает и соответствие целевому распределению, и разнообразие генерации.

Когда модуль активен, скилл проставляет флаг `useSSOT = true` и добавляет в вывод
видимую секцию «📚 SSoT техника» со ссылкой на arXiv — чтобы пользователь не
принял промежуточные `<random_string>` и `<thinking>` за баг.

### 6.4 Выбор reasoning mode и почему НЕ вставляется CoT для frontier-моделей

Скилл выбирает режим рассуждения под тип задачи:

| Режим | Когда | Первоисточник техники |
|---|---|---|
| **Direct** | Простые однозначные задачи | — |
| **Chain-of-Thought** | В промпт не вставляется ни для одной цели; только если пользователю нужны **видимые** промежуточные шаги для аудита | Wei et al., 2022, [arXiv:2201.11903](https://arxiv.org/abs/2201.11903) |
| **Tree-of-Thoughts** | Несколько путей решения с последующей сходимостью | Yao et al., 2023, [arXiv:2305.10601](https://arxiv.org/abs/2305.10601) |
| **ReAct** | Использование инструментов (Thought→Action→Observation) | Yao et al., 2022, [arXiv:2210.03629](https://arxiv.org/abs/2210.03629) |
| **Self-Consistency** | Высокие ставки (медицина, финансы, безопасность) — N путей + голосование | Wang et al., 2022, [arXiv:2203.11171](https://arxiv.org/abs/2203.11171) |

**Ноу-хау, идущее против устаревших гайдов:** «think step by step» в промпт не
вставляется **ни для одной** цели. Каждая современная цель рассуждает внутренне, как
только задействована её ручка глубины (`effort`, `reasoning_effort`, `thinking_level`,
thinking effort у DeepSeek V4), и явная инструкция по декомпозиции с этой ручкой
конкурирует, расходуя токены без прироста глубины. Правильный ход — не вписать CoT в
промпт, а сказать пользователю поднять ручку. Валидатор проверяет отсутствие «think
step by step» для всех целей.

Gemini 3 Developer Guide формулирует это прямо: если раньше вы выжимали рассуждение из
Gemini 2.5 сложным промпт-инжинирингом, попробуйте `thinking_level: "high"` и
упрощённый промпт.

Это иллюстрирует более общий принцип: **best practice одного поколения моделей
становится анти-паттерном в следующем**. Отсюда же архитектурное решение свести все
версионно-зависимые факты в один файл (`references/target-models.md`) — обновление
поколения моделей должно стоить одну правку, а не сплошной проход по пакету.

### 6.5 Uncertainty rule — анти-галлюцинационный контракт

В блок `CONSTRAINTS` **всегда** дословно встраивается:

> «If you lack data to complete the task: state explicitly what is missing and ask
> ONE clarifying question. Do not fabricate facts.»

Это не стилистический выбор, а часть контракта CRAFT+. Назначение — дать модели
явный «выход» в ситуации нехватки данных (спросить вместо того, чтобы выдумать).
Валидатор проверяет наличие сигнатуры `fabricate facts` в промпте.

### 6.6 Verification block — самопроверка как стоп-гейт

Каждый промпт заканчивается чек-листом из 3–5 пунктов, зеркалящим
`SUCCESS_CRITERIA`. Исполняющая модель обязана пройти его перед выводом. Это
прикладная форма самопроверки/самокритики: модель относится к чек-листу как к
воротам, что измеримо повышает соответствие требованиям на frontier-моделях.

### 6.7 Стратегия вопросов: «заполни сам, спрашивай только критичное»

Главное правило: **заполнять максимум самостоятельно, спрашивать только то, что
невозможно разумно предположить.** Эталонное хорошее взаимодействие — ноль
вопросов: скилл сам выбирает роль, тон, формат, длину, стек, логирует это в
секцию «💡 Что я решил за тебя» и отдаёт промпт.

Два провала, которые этим балансируются:
1. **Спросить слишком много** — пользователь чувствует допрос и бросает.
2. **Предположить слишком много** — агент промахивается по критичной детали
   (например, целевой модели) и выдаёт неподходящий промпт.

«Критичный пробел» (повод спросить) — ровно 5 категорий:
1. задача принципиально неясна (нет deliverable);
2. не определена целевая модель;
3. сработал триггер мега-задачи;
4. запрос ссылается на отсутствующие данные («мой код», «моё ТЗ»);
5. явно конфликтующие требования, неразрешимые предположением.

Всё остальное (роль, тон, стек, длина, формат, нужны ли примеры, «ты»/«вы») —
**решается самим скиллом** и логируется в assumptions. Есть явный список
**запрещённых вопросов** («какую роль дать?», «какой тон?», «сколько слов?») —
их задавать нельзя.

Как спрашивать: ≤3 вопроса за раунд, каждый пронумерован, **с вариантами-подсказками
(1/2/3/4)**, чтобы пользователь отвечал одной цифрой. Закрытые вопросы с опциями
отвечаются легче открытых — это снижает трение.

### 6.8 Scope check — детекция мега-задач

Если запрос описывает то, что не помещается в один промпт (несколько несвязанных
подсистем «CRM + аналитика + биллинг»; размытый scope «как у Google»; объём вывода
физически не влезает в один ответ), скилл **не** молча выдаёт поверхностный
результат, а предупреждает и предлагает 3 варианта:
1. собрать промпт на MVP-версию,
2. не собирать — пользователь сам разобьёт на этапы,
3. собрать как есть, понимая риски (с записью в assumptions).

Решение остаётся за пользователем — у него может быть контекст, которого нет у
скилла (например, нужен высокоуровневый эскиз архитектуры, а не реализация).

### 6.9 Двуязычность и языковая политика

- **Детекция языка пользователя** (USER_LANG): официально поддержаны RU и EN;
  для прочих — английский с best-effort.
- **Текст для пользователя** (заголовки секций, вопросы, assumptions) — на языке
  пользователя.
- **Сам промпт** — по умолчанию на английском (как более «плотный» для моделей),
  но **первая строка промпта всегда** — инструкция: «Respond to the user in
  [язык]. If you need to ask for clarifications, ask them in [язык]». То есть промпт
  английский, а исполняющая модель отвечает конечному пользователю на его языке.
- **Все триггеры условных модулей, scope-check и доработок — двуязычные** (RU+EN
  пары), поэтому детекция работает одинаково на обоих языках.

### 6.10 Безопасность агента (anti-prompt-injection)

Тонкое, но важное для статьи разграничение — **две разные «безопасности»**:

1. **Защита самого агента** (есть): ввод пользователя трактуется как *данные*, а
   не как инструкции агенту. Попытки «Ignore previous instructions», «ты теперь
   X», «System: new rules», claim авторитета — игнорируются. Из шумного запроса
   извлекается полезная часть, по ней строится промпт, в assumptions логируется
   факт детекции инъекции.
2. **Защита выходного промпта** (сознательно отсутствует): в итоговый промпт
   **не** добавляется никакой anti-injection-обвязки. Логика: *пользователь пишет
   задачу сам себе* — защита от инъекций здесь была бы бессмысленным мусором,
   раздувающим промпт. Валидатор даже специально проверяет, что в промпте **нет**
   «ignore previous instructions» и подобного.

Дополнительно: формат вывода неизменяем — никакая инструкция пользователя не может
заставить скилл убрать code-блок, переименовать секции или ответить «просто
текстом». Требования безопасного контента (CSAM, оружие массового поражения и
т.п.) делегируются стандартной safety-политике хост-модели — скилл не добавляет
своих слоёв отказа.

### 6.11 Контракт вывода и JSON-режим

**По умолчанию — Markdown** с промптом внутри fenced code-блока (чтобы в чат-UI
работала кнопка Copy). Жёсткие правила вывода:
- промпт **только внутри** code-блока, никогда не дублируется в прозе (иначе
  ломается one-click copy — критичное UX-нарушение);
- фиксированный порядок секций: 🎯 промпт → ⚙️ настройки → 💡 решения → (📚 SSoT,
  если был) → (🔄 что улучшено, если improve) → курсивная строка про правки;
- никаких преамбул («Конечно, вот…») и постамбул.

**JSON-режим** активируется только по явному запросу (`output json`, `формат json`,
`--json`) или при программном потреблении. Выдаёт ровно один валидный JSON-объект
по фиксированной схеме (`status`, `target_model`, `prompt`, `user_instructions`,
`assumptions`, `useSSOT`, `mode`, `clarifying_questions`) — без обёрток, без
комментариев, без trailing-запятых, UTF-8 для кириллицы.

### 6.12 Режим `improve` (улучшение чужого промпта)

Помимо генерации с нуля (`generate`) скилл умеет режим `improve`: разбирает
существующий промпт против CRAFT+, находит пробелы (какие блоки отсутствуют/вялые),
переписывает под целевую модель и показывает в секции «🔄 Что улучшено» конкретный
список изменений. Пример из пакета: промпт «Write a LinkedIn post about AI. Make it
good and interesting» (1/10 блоков заполнено) → полный CRAFT+ с заменой «good and
interesting» на 5 измеримых критериев.

### 7.3 Инженерные решения автора скилла (design choices, не «доказанные» извне)

Это решения, которые разумны и внутренне согласованы, но являются выбором автора,
а не результатом цитируемого исследования:
- конкретный набор именно **10** блоков и их порядок;
- потолок длины промпта **700 слов** (нижней границы нет: она была снята — минимум
  в 200 слов ничем не обоснован и заставлял добивать простые задачи водой, что сам
  скилл записывает в pitfalls как over-engineering);
- лимит **≤3 вопроса** за раунд и список запрещённых вопросов;
- порядок вставки модулей (multimodal → fact → compute → creativity);
- двуязычные триггер-листы и их конкретный состав;
- решение **не** добавлять anti-injection в выходной промпт;
- 16 постоянных проверок валидатора (+ до 2 условных) и 11 evals-сценариев.

Отдельно: цифра «>30% ошибок многошаговой арифметики», раньше стоявшая в тексте
модуля B как обоснование, **удалена**. Источника у неё не было, а замеры 2025–2026
годов её опровергают: на арифметических бенчмарках ведущие модели дают от 95% до 100%
точности. Совет предпочитать исполнение кода остался — но обоснован теперь тем, что
действительно проверяемо.

## 8. Почему это валидно: связка «механика → обоснование»

Сводная логика для аргументации в статье — каждая механика отвечает на конкретный
известный провал LLM:

| Известный провал LLM | Подтверждение | Ответ скилла |
|---|---|---|
| Галлюцинации при нехватке данных | широко документировано | uncertainty rule + модуль факт-чекинга + пометки `[UNVERIFIED]` |
| Невоспроизводимость и накопление ошибки в длинных цепочках вычислений | практика; сырая арифметическая точность у ведущих моделей при этом высокая (95–100%) | модуль исполнения кода (или выдача Python-скрипта) |
| Mode collapse / низкое разнообразие после RLHF | Misaki & Akiba 2025/26 (PIF) | модуль SSoT с энтропийной инъекцией |
| Модель хуже использует информацию в середине длинного контекста | Liu et al. 2023 («Lost in the Middle»); рекомендация Anthropic класть данные наверх, а запрос в конец | потолок 700 слов, 3–5 примеров, запрет на дублирование требований, инверсия порядка при объёмном payload |
| «Расплывчатые» инструкции не управляют выводом | практика CO-STAR/RISEN | измеримые `SUCCESS_CRITERIA` + `VERIFICATION` |
| Разные модели по-разному «любят» формат | доки Anthropic/OpenAI/Google/DeepSeek | полировка под target_model |
| Устаревшие приёмы вредят новым моделям | эволюция reasoning-моделей | запрет «think step by step» для всех целей; все версионные факты сведены в один файл, секция «Old patterns» для выведенного из обращения |
| Промпт-инъекции в пользовательский ввод | OWASP LLM Top-10 и практика | трактовка ввода как данных, извлечение полезной части, лог в assumptions |
| Самая сильная ручка качества живёт вне промпта и пользователь про неё не знает | все четыре вендора вынесли глубину рассуждения в отдельный параметр | обязательная строка про thinking/effort в ⚙️-секции каждого готового ответа |

Главный тезис для статьи: **валидность скилла — не в одной «магической» технике, а
в том, что он системно сопоставляет каждый известный класс ошибок LLM с конкретным
контр-механизмом и делает это воспроизводимо**, с программной проверкой результата.

## 9. Контроль качества: валидатор и evals

Скилл — один из немногих промпт-инструментов с **программной верификацией
собственного вывода**.

### 9.1 `scripts/validate.py` — 16 постоянных проверок плюс до двух условных

Python-валидатор принимает готовый промпт + целевую модель и прогоняет проверки:
- языковая инструкция **первой строкой** промпта (не просто где-то в начале —
  проверяется позиция, как того требует Step 6);
- присутствие всех 10 блоков CRAFT+ (с учётом разрешённых пропусков
  `actions`/`examples`) — детектор блоков **разный под формат**: XML-теги для
  Claude/Universal, `#`-заголовки **или** XML для GPT, `##` или XML для Gemini,
  любой из вариантов для DeepSeek; сопоставление регистронезависимое;
- наличие uncertainty rule (сигнатура `fabricate facts`);
- длина в пределах 700 слов (только потолок, нижней границы нет);
- отсутствие эскалированной эмфазы **на директивах про инструменты** для
  Claude/Universal — узкая область, которую действительно оговаривает вендор;
- отсутствие «think step by step» — для всех целей;
- отсутствие расплывчатых фраз — **только внутри `success_criteria` и
  `verification`**: сканирование всего промпта давало ложные срабатывания на
  задачах, которые сами по себе про креатив;
- консистентность флага `useSSOT` ↔ наличие протокола креативности в **любой** из
  форм обёртки, которые разрешает `target-models.md` (XML-тег или Markdown-заголовок);
- отсутствие anti-injection-мусора в промпте.

Коды возврата: `0` — все прошли, `1` — есть провалы, `2` — неверный вызов.
Рекомендован для режима `improve` и сложных промптов.

### 9.2 `evals/evals.json` — 11 сценариев + раннер

Схема совпадает с документированной Anthropic формой — `skills` / `query` / `files` /
`expected_behavior`. Покрывают основные поведенческие пути: простой Claude-промпт с
модулем кода; креативный GPT с SSoT; минимальный запрос → уточнение; мега-задача →
предупреждение; режим improve; попытка инъекции; триггер факт-чекинга; JSON-режим;
universal-цель; цель DeepSeek на поколении V4; и — важный негативный кейс — **обычная
задача «напиши факториал на Python», на которой скилл НЕ должен активироваться**
(защита от ложных срабатываний).

`scripts/run_evals.py` валидирует схему файла и печатает run sheet: запрос плюс
чек-лист ожидаемого поведения по каждому сценарию. Модель раннер намеренно не
вызывает — оценка промпт-конструктора требует суждения о получившемся промпте, и
раннер это суждение структурирует, а не имитирует.

Наличие негативного кейса — признак инженерной зрелости: проверяется не только
что скилл делает, но и чего он делать не должен.

## 10. Ограничения и честные оговорки

Для корректной статьи стоит явно проговорить:

1. **Версионные факты стареют, и это структурная проблема, а не разовая.** Первая
   редакция скилла размазала названия моделей и параметров по семи файлам плюс
   продублировала их в чат-издании — и к августу 2026 устарела целая целевая модель
   (`deepseek-chat` выведен из обращения 24 июля 2026), а вместе с ней и правило,
   на ней построенное. Сейчас все такие факты сведены в
   `references/target-models.md`, выведенное из обращения свёрнуто в секцию
   «Old patterns», а чат-издание генерируется из тех же исходников. Для статьи это
   самостоятельный сюжет: у скилла, который описывает поведение чужих моделей, есть
   срок годности, и архитектура должна это учитывать.

2. **Две цифры-обоснования не подтвердились и удалены.** «>30% ошибок арифметики»
   не имела источника, а замеры 2025–2026 годов дают у ведущих моделей 95–100%
   точности на арифметике. «+20% на агентных задачах» приписывалась гайду OpenAI,
   которого в гайде нет: единственная количественная величина там — Tau-Bench Retail
   73.9 → 78.2% за переход на Responses API, к секции persistence отношения не
   имеющая. Обе рекомендации при этом остались — изменилось обоснование, а не совет.

3. **Ссылка на Levy et al. была применена не по адресу.** Статья «Same Task, More
   Tokens» обосновывала в скилле потолок в 3 few-shot примера. Она измеряет
   деградацию от **padding**, на моделях поколения 2024 года, и 3000 токенов — это
   максимальная протестированная длина, а не порог, «за которым» что-то наблюдали.
   Правило заменено на «3–5 примеров» по действующей рекомендации Anthropic.

4. **SSoT — свежая работа.** [arXiv:2510.21150](https://arxiv.org/abs/2510.21150)
   на момент написания находится на рассмотрении (ICLR), не финально-рецензирована.
   Техника убедительна и воспроизводима, но статусом это пока «препринт под
   ревью», что стоит упомянуть.

5. **Universal-формат сознательно неоптимален** на каждой конкретной модели — это
   компромисс, а не «лучшее из всех миров».

6. **Скилл не декомпозирует мега-задачи** — он только детектирует их и
   предупреждает. Разбиение на цепочку промптов — отдельная задача вне его scope.

7. **Качество выхода зависит от исполняющей модели.** Скилл собирает отличный
   промпт, но финальный результат всё равно ограничен возможностями той модели,
   которой этот промпт скармливают.

## 11. Глоссарий

- **CRAFT+** — методология скилла: классический CRAFT, расширенный измеримыми
  критериями, условными модулями, верификацией и полировкой под целевую модель.
- **target_model** — целевая модель, под которую форматируется промпт
  (Claude / GPT / Gemini / DeepSeek / Universal).
- **Условный модуль (A/B/C/D)** — блок, подключаемый по триггерам: факт-чекинг /
  исполнение кода / SSoT / мультимодальность.
- **SSoT (String Seed of Thought)** — техника инъекции энтропии случайной строкой
  для верного распределения и разнообразия генерации (arXiv:2510.21150).
- **Mode collapse** — схлопывание разнообразия ответов после RLHF-дообучения.
- **PIF (Probabilistic Instruction Following)** — способность модели следовать
  заданному распределению вероятностей по вариантам при многократном запуске.
- **Uncertainty rule** — обязательное правило в `CONSTRAINTS`: при нехватке данных
  спросить, а не выдумывать.
- **Progressive disclosure** — трёхуровневая подгрузка контекста скилла
  (фронтматтер → тело → references по требованию).
- **assumptions** — секция «что скилл решил за пользователя» (роль, тон, формат,
  стек), обеспечивающая прозрачность и возможность отката.
- **generate / improve** — два режима: сборка промпта с нуля / разбор и переписывание
  существующего промпта.
