# Pepper Orchestrator 0.13.0 — автономность Codex CLI и Claude Code

29–30 октября 2026 года. Публичный preview-релиз `pepper-orchestrator-v0.13.0`.
Поставки в пользовательские программы и операций с PROD/БД нет.
Codex-часть проверена на macOS (живой цикл) и в CI; Claude-часть — на Linux (живой цикл) и в CI.

## Реализовано

- Общий канонический runtime; автономность включается явно для локальных программ Codex CLI
  и Claude Code (один клиент на программу, один хост).
- Реестр v2: индекс WP, история сессии, подтверждение процесса/конфигурации, сохранение
  прежних привязок и незавершённого outbox. Неизвестные старые сессии не становятся доверенными.
- Один координатор с поколением владения. Сессия, слот, назначение и блокировки резервируются
  в общей транзакции с CAS; сеть выполняется вне короткого state-lock.
- `next --json`, совместимые волны, структурированный dispatch, assign/send/started/reconcile.
  Постановка в очередь сохраняет DISPATCHING; IN_PROGRESS требует подтверждения исполнителя.
- Постоянный assignment ID, защита от повторной отправки, раннего STARTED и устаревшего
  координатора. Неизвестный исход сохраняет резервирование; слепой OWNER HANDOVER запрещён.
- Reuse чистого worktree после подтверждённого merge. Полный локальный HEAD сверяется с
  принятой ревизией и PR, включая squash merge и удалённую remote-ветку. ACCEPTED недостаточно.
- Исполнитель меняет ветку и готовит окружение, сохраняя техническую квитанцию в runtime.
  Защищённый `.codex` не переписывается; изменение настроек в новой базе требует подготовки
  владельцем. Неизвестный исход setup не вызывает слепой повтор.
- Локальный наблюдатель, объединение сигналов, consume, пауза/close, восстановление на resume,
  сообщения о разрешениях, циклических зависимостях и завершении. Наблюдатель не делает dispatch.
- Компактизация через поддерживаемый API с проверкой события завершения.

Настройки по умолчанию: выключено до явного enable; reuse auto, два активных/зарезервированных
модульных слота, 600 секунд до повторной проверки доступного действия. Новые терминалы запускает
владелец по подготовленной команде. Полномочия доставки, sandbox и approvals не расширяются.

Команды и восстановление описаны в [протоколе автономности](../../plugins/pepper-orchestrator/skills/pepper-orchestrator/references/autonomy.md).

## Claude Code: транспорт и реализация

Проба транспорта (Claude Code 2.1.312, Ubuntu 24.04, две одноразовые интерактивные сессии):

| Факт | Наблюдение |
|---|---|
| Наблюдение | `claude agents --json`: PID, sessionId, name, cwd, startedAt, `idle/busy/waiting`, `waitingFor`; sessionId сохраняется после `/compact` |
| Пробуждение исполнителя | `SendMessage` свободной сессии того же класса прав с `crossSessionInbound: accept` начал ход без человека |
| Другой класс прав | Сообщение удерживается для человека: снаружи `waiting / permission prompt`; ответ STARTED тоже удерживается |
| Результат отправки | Одинаков для idle и busy: «в inbox, ещё не прочитано» — это постановка в очередь, не старт |
| Повтор | Байт-в-байт повтор от того же отправителя клиент отбросил сам |
| Monitor | Строка stdout будит координатора; срок не более 30 минут, затем одно уведомление |
| Monitor и статус | Сессия с работающим Monitor видна как `busy` у пустого приглашения — наблюдатель Claude не ждёт idle координатора |
| Компактизация | Slash-команды в сообщениях не выполняются; `/compact`, набранный владельцем, вызывает PostCompact с session_id, cwd, trigger |
| Идентичность | В Bash сессии доступны `CLAUDE_CODE_SESSION_ID` и `CLAUDE_PID` |

Реализация на общем ядре (`autonomy.py`) и `claude_adapter.py`:

- Статус Claude нормализуется к общей схеме: `waiting` — занят, отсутствие в списке — `notLoaded`.
  Подключение сверяет PID живой сессии с подтверждаемым процессом; смена PID/startedAt требует
  повторного подтверждения. Модель и effort не наблюдаемы: сравниваются с подтверждёнными владельцем
  значениями запуска (`attach --model/--effort`).
- Доставка: `dispatch --json` фиксирует намерение отправки и возвращает `send_required`;
  координатор вызывает `SendMessage` и записывает `session sent` (`queued`; `not_sent` только при
  явном отказе; иначе `outcome_unknown`). Сбой между ними оставляет неизвестный исход и резервирование.
- Старт: `session transition` проверяет `CLAUDE_CODE_SESSION_ID`, процесс `CLAUDE_PID` и то, что он
  является предком самого transition, записывает их в квитанцию; `session started` принимает квитанцию и фактическую ветку, пересланный STARTED
  сохраняется как дополнительное свидетельство. Изменение отслеживаемых `.claude/` или `.mcp.json` в новой
  базе требует подготовки владельцем.
- Наблюдатель запускается координатором под Monitor (`autonomy watch --stdout`), печатает только
  сигналы, ошибки наблюдения и остановку; второй процесс наблюдателя отклоняется.
- Компактизация: `session compact` выдаёт владельцу строку `/compact`, повторный вызов подтверждает
  квитанцию PostCompact-хука модуля; до этого reuse заблокирован. `/clear` не автоматизируется.
- Настройки модуля (с `skill_dir`) получают узкое правило `session transition` и PostCompact-хук;
  POSIX-формат 0.7.0 без них не изменился. Запреты merge/deploy/PROD/БД не ослаблены.

Независимое ревью дифа (`/code-review`, high) нашло 10 замечаний; исправлены: падение на
завершившейся сессии, расхождение команды TASK и allow-правила, наблюдение под state-lock,
подделка квитанции через переменные окружения (проверка предка), наблюдатель прежнего поколения
координатора, неполный список нативной конфигурации, отсутствие `--pid`, лишняя работа на тике,
дубль подготовки reuse. Правила автономности присутствуют в каждом файле модуля и неактивны без TASK.

## Живая приёмка итогового архива

Использованы настоящий локальный App Server, две модульные сессии и отдельный координатор.
Наблюдатель будил этого координатора; он самостоятельно выполнял consume, dispatch и сверку STARTED.
Драйвер владельца проверял файлы, создавал PR, фиксировал принятую SHA и выполнял merge только
в одноразовом приватном репозитории. Драйвер не делал dispatch пакетов.

- [WP-A-02](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/3)
  и [WP-B-02](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/4)
  реально исполнялись параллельно: окна ходов App Server перекрываются на 32 секунды.
- [WP-A-03](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/5)
  начался в той же A-сессии/worktree на новой ветке после принятия и squash merge A-02.
  Зависимость снялась без пользовательского `/dispatch`.
- Remote-ветки после merge удалялись; локальные принятые HEAD сохранялись и проверялись.
- После паузы поддерживаемая компактизация завершилась подтверждённым contextCompaction event.
- Тестовые сессии архивированы, серверы и наблюдатели остановлены; приватные тестовые
  репозитории, включая CI, архивированы с сохранением PR и журналов.

Тестовый профиль — workspace-write/on-request с сетью для RPC/GitHub. Исполнители делали fetch
из локального bare mirror; реальные GitHub push/PR/merge выполнял драйвер владельца. Это не
проверка самостоятельного сетевого push модулей или интерактивного согласования владельца.

При первых опытах обнаружены и учтены: недоступность настроенной модели для CLI-аккаунта,
отказ сокета при запрещённой сети, инвалидирование подтверждения после изменения config,
защита `.codex` от записи и временный HTTP 429. Для тестов явно выбрана доступная модель
`gpt-6-astra` из `model/list`; автоматического model fallback в продукт не добавлено.
Отдельный повтор после 429 выполнялся в том же треде только после сверки, что неуспешный ход
не совершил действий. Последний живой запуск итогового ZIP завершился PASS.

## Живая приёмка Claude Code

Linux (Ubuntu 24.04), Claude Code 2.1.312, модель `sonnet`, режим разрешений `auto` у всех сессий,
настройки, сгенерированные программой. Координатор и две модульные сессии — интерактивные `claude`
в отдельных tmux-окнах; `scripts/test-orchestrator-autonomy-live-claude.py`. Драйвер владельца
проверял файлы, создавал PR, фиксировал принятую SHA, делал squash merge и удалял remote-ветки в
одноразовом приватном репозитории и набирал `/compact`, как владелец; dispatch он не выполнял.

Итоговый прогон из собранного `pepper-orchestrator.zip` — **PASS**, без вмешательства драйвера в
работу координатора и без отказов в разрешениях:

- [WP-A-02](https://github.com/ITSalt/pepper-orchestrator-claude-autonomy-20261030-08e881/pull/3) и [WP-B-02](https://github.com/ITSalt/pepper-orchestrator-claude-autonomy-20261030-08e881/pull/4) исполнялись параллельно: обе модульные сессии одновременно
  были `busy` при пакетах в DISPATCHING/IN_PROGRESS. Координатор сам выполнил consume, dispatch,
  `SendMessage`, `session sent` и `session started` по сигналам своего Monitor.
- [WP-A-03](https://github.com/ITSalt/pepper-orchestrator-claude-autonomy-20261030-08e881/pull/5) начался в той же A-сессии и worktree на новой ветке `test/wp-a-03-third` от
  свежей базы после принятия и squash merge A-02; зависимость снялась без пользовательского `/dispatch`.
- Remote-ветки после merge удалялись; принятые HEAD сверялись по фактам Git и PR.
- После паузы `session compact` выдал владельцу строку `/compact`; набранная команда вызвала
  PostCompact-хук модуля, повторный `session compact` подтвердил квитанцию.
- Тестовые tmux-сессии остановлены, приватный репозиторий архивирован.

Отладочный прогон из исходников перед этим тоже завершился PASS, но с вмешательством: он выявил, что
сессия с работающим Monitor видна как `busy`, и наблюдатель ждал idle координатора. После исправления
процесс наблюдателя был перезапущен владельцем. Там же модуль сообщил неверную ветку коммита — факты
Git показали верную, а составная команда с `transition` была отклонена классификатором режима auto;
TASK теперь требует отдельного вызова. Отладочный приватный репозиторий также архивирован.

API не показывает все действующие права/MCP/настройки процесса. Подтверждение фиксирует
доступные факты и свидетельство владельца, но не обещает полной интроспекции скрытых изменений.
Outbox и протокол получателя не объявляются безусловной гарантией exactly-once.
