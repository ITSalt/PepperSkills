# Pepper Orchestrator 0.13.0 — автономность Codex CLI

29 октября 2026 года. Локальный кандидат в ветке `codex/orchestrator-trusted-delivery`.
Публичного релиза, поставки в пользовательские программы и операций с PROD/БД нет.

## Реализовано

- Общий канонический runtime; автономность включается явно только для локального Codex.
- Реестр v2: индекс WP, история сессии, подтверждение процесса/конфигурации, сохранение
  прежних привязок и незавершённого outbox. Неизвестные старые сессии не становятся доверенными.
- Один координатор с поколением владения. Сессия, слот, назначение и блокировки резервируются
  в общей транзакции с CAS; сеть выполняется вне короткого state-lock.
- `next --json`, совместимые волны, структурированный dispatch, assign/send/started/reconcile.
  Постановка в очередь сохраняет DISPATCHING; IN_PROGRESS требует подтверждения исполнителя.
- Постоянный assignment ID, защита от повторной отправки, раннего STARTED и устаревшего
  координатора. Неизвестный исход сохраняет резервирование; слепой OWNER HANDOVER запрещён.
- Reuse чистого worktree после подтверждённого merge. Полный локальный HEAD сверяется с
  принятой ревизией и PR, включая squash merge и удалённую remote-ветку. ACCEPTED недостаточно.
- Исполнитель меняет ветку и готовит окружение, сохраняя техническую квитанцию в runtime.
  Защищённый `.codex` не переписывается; изменение настроек в новой базе требует подготовки
  владельцем. Неизвестный исход setup не вызывает слепой повтор.
- Локальный наблюдатель, объединение сигналов, consume, пауза/close, восстановление на resume,
  сообщения о разрешениях, циклических зависимостях и завершении. Наблюдатель не делает dispatch.
- Компактизация через поддерживаемый API с проверкой события завершения.

Настройки по умолчанию: выключено до явного enable; reuse auto, два активных/зарезервированных
модульных слота, 600 секунд до повторной проверки доступного действия. Новые терминалы запускает
владелец по подготовленной команде. Полномочия доставки, sandbox и approvals не расширяются.

Команды и восстановление описаны в [протоколе автономности](../../plugins/pepper-orchestrator/skills/pepper-orchestrator/references/autonomy.md).

## Живая приёмка итогового архива

Использованы настоящий локальный App Server, две модульные сессии и отдельный координатор.
Наблюдатель будил этого координатора; он самостоятельно выполнял consume, dispatch и сверку STARTED.
Драйвер владельца проверял файлы, создавал PR, фиксировал принятую SHA и выполнял merge только
в одноразовом приватном репозитории. Драйвер не делал dispatch пакетов.

- [WP-A-02](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/3)
  и [WP-B-02](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/4)
  реально исполнялись параллельно: окна ходов App Server перекрываются на 32 секунды.
- [WP-A-03](https://github.com/ITSalt/pepper-orchestrator-autonomy-20261029-a5e22b/pull/5)
  начался в той же A-сессии/worktree на новой ветке после принятия и squash merge A-02.
  Зависимость снялась без пользовательского `/dispatch`.
- Remote-ветки после merge удалялись; локальные принятые HEAD сохранялись и проверялись.
- После паузы поддерживаемая компактизация завершилась подтверждённым contextCompaction event.
- Тестовые сессии архивированы, серверы и наблюдатели остановлены; приватные тестовые
  репозитории, включая CI, архивированы с сохранением PR и журналов.

Тестовый профиль — workspace-write/on-request с сетью для RPC/GitHub. Исполнители делали fetch
из локального bare mirror; реальные GitHub push/PR/merge выполнял драйвер владельца. Это не
проверка самостоятельного сетевого push модулей или интерактивного согласования владельца.

При первых опытах обнаружены и учтены: недоступность настроенной модели для CLI-аккаунта,
отказ сокета при запрещённой сети, инвалидирование подтверждения после изменения config,
защита `.codex` от записи и временный HTTP 429. Для тестов явно выбрана доступная модель
`gpt-6-astra` из `model/list`; автоматического model fallback в продукт не добавлено.
Отдельный повтор после 429 выполнялся в том же треде только после сверки, что неуспешный ход
не совершил действий. Последний живой запуск итогового ZIP завершился PASS.

## Артефакты и границы

Путь: `dist/pepper-orchestrator/0.13.0/`. Итоговые архивы побайтово совпали с архивами полного
локального check; эти же хеши зафиксированы нативным Windows CI:

```text
ce732841a8e260f78ec4e6a0c39a8dd6e8057393ffda24fbde0de508ff1f9d9b  pepper-orchestrator.plugin.zip
936ac843379c442f3c42f063ba8a836733bc674db37f3d5ea7f79c317ed10086  pepper-orchestrator.zip
```

Живое исполнение модулей проверено на macOS. Нативные Windows/Linux E2E-циклы reuse не проводились;
их offline/native smoke результаты выше не подменяют такую приёмку. Пользовательский PROD,
реальные миграции, Claude autonomy, #23, ранний reuse после ACCEPTED, смешанные клиенты,
несколько хостов и постоянный системный сервис исключены из этой поставки.

API не показывает все действующие права/MCP/настройки процесса. Подтверждение фиксирует
доступные факты и свидетельство владельца, но не обещает полной интроспекции скрытых изменений.
Outbox и протокол получателя не объявляются безусловной гарантией exactly-once.
