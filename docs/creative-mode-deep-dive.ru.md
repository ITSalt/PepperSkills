> Это **не статья**, а материал-источник для неё. Здесь собрано: на чём основан скилл,
> что в первоисточнике реально доказано, что о технике говорят третьи стороны, где
> критика, где противоречия и какие есть альтернативы.

> Все данные первоисточника сверены с полным текстом статьи (arXiv HTML v3), а не с
> пересказами. Таблицы декодированы вручную и проверены на согласованность по
> контрольным процентам, которые авторы приводят в тех же ячейках.

Каждое утверждение помечено уровнем доказательности. Это главное, что писателю нужно
соблюсти: разные теги требуют разных формулировок в тексте статьи.

| Тег | Что означает | Как писать в статье |
|---|---|---|
| `[СТАТЬЯ]` | Есть в arXiv:2510.21150, с указанием таблицы/раздела | «Авторы измерили…», можно давать цифру как факт |
| `[ПРОВЕРЕНО]` | Подтверждено вторым источником или моим расчётом в этой сессии | Можно давать как факт, желательно указать способ проверки |
| `[ИСТОЧНИК]` | Из внешней публикации (другая статья, блог, СМИ) | «По данным X…» — обязательна атрибуция |

| `[АНАЛИТИК]` | Моя интерпретация; внешнего источника нет | «Можно предположить…», не подавать как установленный факт |

## 1. Объект разбора: что делает скилл

`pepper-creative-mode` — портирование академической техники в формат переносимого
скилла. Файлы: [`pepper-creative-mode/anthropic/SKILL.md`](../pepper-creative-mode/anthropic/SKILL.md),
четыре reference-файла, четыре примера, плюс два варианта под OpenAI.

**Протокол.** Каждый ответ состоит ровно из трёх секций:

```text
<random_string> [16+ символов, разные классы символов] </random_string>
<thinking>      [детерминированная арифметика над строкой, все шаги] </thinking>
<answer>        [только финальный ответ] </answer>
```

**Два режима.**
- **PIF** (Probabilistic Instruction Following) — сэмплирование из заданного
  распределения: монетка, кубик, взвешенный выбор, Nash equilibrium.
- **DAG** (Diversity-Aware Generation) — творческая генерация, где нужно
  разнообразие между прогонами.

**Три арифметических паттерна** (скилл предписывает выбор по типу задачи):
- **Sum-Mod** — `sum(ord(c)) mod N`, для равновероятных исходов.
- **Rolling Hash** — `h = (h*31 + ord(c)) mod M`, для неравных вероятностей.
- **Decision Cascade** — разбить творческий ответ на 2–5 компонент, каждую выбрать
  Sum-Mod'ом по своему непересекающемуся сегменту строки, собрать вместе.

**Жёсткие правила скилла:** строка генерируется внутренне (никаких внешних PRNG);
минимум 16 символов и все четыре класса символов; новая строка на каждое независимое
решение; арифметика показывается полностью; строку и вычисление нельзя переигрывать
после того, как увидел результат.

## 2. Первоисточник: String Seed of Thought

`[СТАТЬЯ]` Misaki, K., Akiba, T. **«String Seed of Thought: Prompting LLMs for
Distribution-Faithful and Diverse Generation»**, Sakana AI.
arXiv:2510.21150 · OpenReview `luXtbX1lVK` · страница проекта `pub.sakana.ai/ssot/`.

- v1 — 24 октября 2025, v2 — 7 ноября 2025, v3 — 5 февраля 2026.
- Поле Comments на arXiv: **«Accepted to ICLR 2026»**. Принятие подтверждается также
  страницей проекта (датирована апрелем 2026) и сторонними разборами. `[ПРОВЕРЕНО]`

### Постановка задачи (цитаты авторов)

`[СТАТЬЯ]` **PIF:** *«a task requiring an LLM to select its answer from a predefined set
of options, each associated with a specific probability, such that the empirical
distribution of the generated answers aligns with the target distribution when prompted
multiple times»*.

`[СТАТЬЯ]` **DAG:** задачи, где *«the goal is to generate a diverse set of solutions while
preserving quality»* — придумывание имён, написание историй, брейнсторм.

`[СТАТЬЯ]` Ключевая мысль постановки: модель **знает** нужное распределение, но не умеет
из него **сэмплировать**. Авторы отдельно отделяют это от калибровки: *«Calibration uses
token probabilities to align confidence with accuracy on single-answer tasks, whereas our
method performs actual sampling from an explicit target distribution over multiple
acceptable answers»*.

### Сам метод — дословный системный промпт авторов

`[СТАТЬЯ]` (Appendix A, PIF-вариант, сокращённо по смыслу — полный текст в Приложении А
этого досье):

> You are a helpful AI Assistant… If the task involves probabilistic or non-deterministic
> reasoning, you must begin by generating a unique and complex random string to serve as
> a seed. This random string should appear sufficiently complex and unpredictable, with
> no obvious structure or pattern… Make sure to extract maximum randomness from the
> string by using all of its content.

**Критично для понимания разницы со скиллом** `[СТАТЬЯ]`:
- Промпт **не задаёт** ни длину строки, ни набор символов.
- Промпт **не предписывает** конкретную арифметику.
- Sum-Mod и Rolling Hash — это **не инструкции авторов, а стратегии, которые модели
  придумали сами**, и которые авторы затем классифицировали, анализируя цепочки
  рассуждений. Формулировка авторов: модель *«adapts its strategy to the task: for
  unbiased distributions, it favors the simple Sum-Mod method, but for biased
  distributions, it often adopts the more sophisticated rolling hash»*.

## 3. Что именно доказано: цифры

### 3.1 PIF — основной результат (Table 1)

`[СТАТЬЯ]` Метрика — JS-дивергенция между эмпирическим и целевым распределением,
**в единицах 10⁻³** (меньше — лучше). Протокол: 100 испытаний в серии, 10 серий,
приводится среднее ± σ. Температуры: deepseek-v3 и gpt-4o — 1.0; QwQ-32B и deepseek-r1 — 0.6.

Задачи: 2-choice (`heads/tails`, 50/50), biased 2-choice (30/70), 3-choice (RPS, по 1/3),
biased 3-choice (10/20/70), biased 9-choice.

| Модель | Метод | 2-choice | biased 2 | 3-choice | biased 3 | biased 9 |
|---|---|---|---|---|---|---|
| deepseek-v3 | Baseline | 5.97 | 111.45 | 136.03 | 117.28 | 297.33 |
| deepseek-v3 | **SSoT** | 2.91 ↓51% | 3.54 ↓97% | 15.33 ↓89% | 15.65 ↓87% | 44.90 ↓85% |
| gpt-4o | Baseline | 15.56 | 117.28 | 60.55 | 113.06 | 290.25 |
| gpt-4o | **SSoT** | 4.41 ↓72% | 9.59 ↓92% | 7.09 ↓88% | 9.75 ↓91% | 34.15 ↓88% |
| o4-mini-high | Baseline | 3.30 | 86.12 | 67.14 | 115.53 | 61.60 |
| o4-mini-high | **SSoT** | 0.94 ↓71% | 13.13 ↓85% | 10.34 ↓85% | 17.35 ↓85% | 18.67 ↓70% |
| QwQ-32B | Baseline | **2.43** | 109.51 | 104.64 | 108.73 | 260.59 |
| QwQ-32B | **SSoT** | **3.39 ↑40%** | 2.47 ↓98% | 1.82 ↓98% | 1.30 ↓99% | 11.48 ↓96% |
| deepseek-r1 | Baseline | 36.09 | 69.58 | 106.30 | 49.53 | 138.21 |
| deepseek-r1 | **SSoT** | 3.03 ↓92% | 1.51 ↓98% | 4.98 ↓95% | 4.30 ↓91% | 18.06 ↓87% |
| **PRNG (эталон)** | — | **1.85** | **1.93** | **3.36** | **2.85** | **13.72** |

**Как это читать для статьи:**
- Эффект на **смещённых** распределениях огромный и стабильный: 85–99 % снижения у всех
  пяти моделей. Это самый твёрдый результат работы.
- На **равновероятной монетке** картина пёстрая: от ↓92 % (deepseek-r1) до ↑40 %
  (QwQ-32B). Одна из пяти моделей стала хуже.
- `[АНАЛИТИК]` Причина разброса видна прямо в таблице: у QwQ-32B baseline на монетке уже
  2.43 — это **лучше**, чем у PRNG-эталона в трёх из пяти задач. Улучшать там нечего, а
  арифметика добавляет свой шум. Это не аномалия модели, а закономерность: чем ближе
  baseline к идеалу, тем меньше смысла в SSoT.

### 3.2 DAG — разнообразие (Table 2, NoveltyBench curated)

`[СТАТЬЯ]` Формат ячейки: **Distinct (Utility)**, больше — лучше.

| Метод | Overall Distinct | (Utility) |
|---|---|---|
| Baseline | 4.70 | (5.17) |
| Paraphrase | 5.63 | (5.57) |
| **T = 0.8** | 5.03 | (5.52) |
| **T = 1.0** | 5.57 | **(6.03)** |
| **SSoT** | **6.19** | (5.92) |

`[СТАТЬЯ]` На WildChat (Table 3): baseline 3.39 (4.08) → SSoT 5.25 (4.86).

**Это самая недооценённая таблица работы, и для статьи она важнее всех остальных**
`[АНАЛИТИК]`: простое поднятие температуры до 1.0 даёт 5.57 Distinct при Utility 6.03 —

SSoT выигрывает по Distinct, но не выигрывает по Utility у такой примитивной альтернативы,
как «поставь температуру 1.0». Честная формулировка для статьи: SSoT покупает
последние ~10 % разнообразия ценой небольшой потери качества.

| Метод | 2-choice | biased 2 | 3-choice | biased 3 | biased 9 |
|---|---|---|---|---|---|

## 4. Почему это вообще работает: механизм

`[СТАТЬЯ]` **Ключевая цитата, объясняющая, почему нельзя «думать про себя»:**

> *«Crucially, similar to zero-shot CoT, explicitly instructing the model to write out the
> manipulation process in the output is vital; otherwise, reasoning models may hallucinate
> the derivation without actually using the string.»*

То есть модель, которой не велели показать выкладку, **делает вид**, что посчитала, а на
деле выдаёт привычный ответ. Это прямое обоснование жёсткого правила скилла «показывай
арифметику полностью».

`[СТАТЬЯ]` **Теория.** В Appendix G авторы доказывают границы на total variation distance
для sum-mod-стратегии: верхняя граница убывает с ростом длины строки n и числа
испытаний K.

`[СТАТЬЯ]` **Качество самой строки авторы проверяли.** Figure 7: равномерность
сгенерированных моделью целых чисел (0–127) улучшается по мере роста числа
thinking-токенов; сложность строки (нормализованная Lempel-Ziv, степень сжатия zlib)
тоже растёт с длиной рассуждения. Figure 12: униграммное распределение символов в строке
спадает **примерно линейно**, а не степенным законом.

`[СТАТЬЯ]` **Остаточная зависимость между символами** (Table 12) — TV-расстояние между
совместным распределением и произведением маргиналов:

| modulo m | лаг 1 | лаг 2 | лаг 3 |
|---|---|---|---|
| 2 | 0.0164 | 0.0042 | 0.0249 |
| 3 | 0.0275 | 0.0204 | 0.0051 |
| 9 | 0.0645 | 0.0513 | 0.0409 |

Символы не полностью независимы, и зависимость растёт с ростом модуля.

### 4.1 Собственный расчёт: узкое место — не энтропия строки

`[ПРОВЕРЕНО]` Я смоделировал арифметику скилла на строках, символы которых берутся из
**намеренно перекошенных** распределений (скрипт — Приложение В; 60 000 прогонов на
точку). Вопрос: насколько перекос символов портит результат `sum(ord) mod N`.

JS-дивергенция от равномерного, ×10⁻³:

| Распределение символов | N | len=1 | len=2 | len=4 | len=16 |
|---|---|---|---|---|---|
| линейный спад (как на Figure 12) | 2 | 0.010 | 0.007 | 0.002 | 0.001 |
| линейный спад | 6 | 0.384 | 0.008 | 0.025 | 0.009 |
| жёсткий перекос (80 % массы на 5 символах) | 2 | 2.631 | 0.031 | 0.000 | 0.002 |
| жёсткий перекос | 6 | 11.329 | 0.148 | 0.009 | 0.003 |

`[АНАЛИТИК]` **Вывод, который стоит вынести в статью.** Суммирование по модулю —
классический перемешиватель: при независимых символах любой перекос «отмывается» уже на
длине 2–4. Если бы всё упиралось в энтропию строки, хватило бы четырёх символов. Но
эмпирически (Table 7) нужно 16–24. Значит, ограничивающий фактор — **не качество строки**,
а два других: остаточная зависимость между символами (Table 12) и то, насколько добросовестно
модель выполняет арифметику. Это, кстати, опровергает самый расхожий вариант критики
(см. раздел 8.1).

## 5. Родословная проблемы: независимые подтверждения

Что LLM плохо сэмплируют — установлено независимо от Sakana, и это надо показать в статье,
иначе выглядит как «авторы придумали проблему под своё решение».

`[ИСТОЧНИК]` **Gu et al., COLING 2025, «Do LLMs Play Dice?»** — работа, на которую SSoT
прямо ссылается. Вывод: агенты **понимают** вероятности, но не умеют из них
**сэмплировать**; точность улучшается с использованием кода, но остаётся недостаточной
для симуляции поведения людей.

`[ИСТОЧНИК]` **Meister, Guestrin, Hashimoto, NAACL 2025, «Benchmarking Distributional
Alignment of Large Language Models»** — вторая опорная ссылка SSoT. Показано, что модели
часто не могут воспроизвести распределение, даже когда способны его описать словами.

`[ИСТОЧНИК]` **Zhao, Du, Wang, arXiv:2601.05414, «Large Language Models Are Bad Dice
Players»** (2026) — крупнейший на сегодня аудит: 11 моделей, 15 распределений.
Batch-генерация проходит статистические тесты в **7 % случаев (медиана)**; при
независимых запросах **10 из 11 моделей не проходят ни одного распределения**. Вывод
авторов: у моделей нет функционального внутреннего сэмплера, для статистических гарантий
нужны внешние инструменты.

`[ИСТОЧНИК]` **arXiv:2603.02202, «Frontier Models Can Take Actions at Low
Probabilities»** (2026, GPT-5 / Claude-4.5 / Qwen-3). Косвенно, но сильно подтверждает
механизм SSoT: при доступе к **внешней энтропии (UUID)** модели удерживают калибровку на
уровне реже 1 из 100 000; без внешней энтропии некоторые дотягивают до 1 из 10 000; и
успех зависит от **явного chain-of-thought**. Тот же рецепт: источник энтропии + выписанное
вслух вычисление.

`[ПРОВЕРЕНО]` **Русскоязычный бытовой пример для затравки статьи.** Habr, «Умеет ли Алиса
AI выдавать случайное число?»: при запросе 500 случайных чисел из диапазона 1–500 числа
**1–9 не выпадали практически никогда**; при запросе 100 чисел из 1–100 модель выдала все
числа по одному разу в перемешанном порядке — то есть перестановку, а не выборку.

## 7. Противоречия и непроверенные утверждения

### 7.1 «Модели выдают heads в ~78 % случаев» — это не измерение

`[ПРОВЕРЕНО]` Цифра 78 % присутствует в `SKILL.md` дважды и в `examples/fair-coin.md`,
поданная как эмпирический факт про frontier-модели. В самом тексте статьи (arXiv v3)
**строки «78» в этом значении нет вообще**.

Источник цифры — инфографика на странице проекта `pub.sakana.ai/ssot/`, блок «Without
SSoT: 78 % H / 22 % T», «With SSoT: 51 % H / 49 % T». Прямо под этой инфографикой
авторы написали:

> *«(Percentages and outputs shown here are illustrative examples, not measured values.)»*

`[ПРОВЕРЕНО]` **Той же оговоркой закрыт и второй яркий образ скилла** — «все басни
схлопываются в зайца с черепахой». Это соседний блок той же иллюстрации («A tortoise and
hare…» ×3), тоже помеченный как иллюстративный.

**Для статьи.** Это лучший из имеющихся сюжетов о том, как research-факты мутируют по
дороге в прикладной инструмент: заведомо условная картинка на лендинге через одну
перепечатку становится «измеренным фактом» в документации скилла. Если нужна реальная
цифра — берите из независимых работ (раздел 5) и указывайте модель и условия.

### 7.2 Причинно-следственная рамка взята из другой работы

`[ПРОВЕРЕНО]` `SKILL.md` объясняет: *«The root causes are RLHF-induced mode collapse,
typicality bias in preference data, and tokenization asymmetries»*. В тексте SSoT
**ноль вхождений** слов `typicality` и `RLHF`. Авторы SSoT вообще не претендуют на
объяснение первопричины — они фиксируют симптом и лечат его.

`[ИСТОЧНИК]` Рамка «typicality bias в preference-данных» принадлежит другой работе —
**Verbalized Sampling** (arXiv:2510.01171), где она формализована как
`r(x,y) = r_true(x,y) + α·log π_ref(y|x) + ε(x)` и измерена на HelpSteer:
**α = 0.57 ± 0.07**.

Само по себе объединение двух работ в одном объяснении не ошибка — но статья должна
называть вещи своими именами: это **синтез автора скилла**, а не вывод Sakana.

### 7.3 Утверждение про токенизацию — опровергнуто

`[ПРОВЕРЕНО]` Проверил напрямую через `tiktoken` (0.13.0):

| Строка | cl100k_base | o200k_base |
|---|---|---|
| `heads` | **1 токен** | **1 токен** |
| `tails` | **1 токен** | **1 токен** |
| ` heads` | 1 | 1 |
| ` tails` | 1 | 1 |
| `Heads` | 2 | 1 |
| `Tails` | 2 | 2 |

Утверждение скилла «"heads" is one token, "tails" is two» **неверно** для строчных форм в
обоих актуальных токенизаторах OpenAI. Асимметрия существует только для формы с
заглавной буквы в `o200k_base` (`Heads` = 1, `Tails` = 2) — а в `cl100k_base` там 2 против 2.
Формулировка в статье допустима только с точным указанием токенизатора и регистра.

### 7.4 Формулировка про статус публикации внутри репозитория

`[ПРОВЕРЕНО]` `pepper-creative-mode/anthropic/SKILL.md` пишет «accepted ICLR 2026» —
это **верно** (поле Comments на arXiv, страница проекта, сторонние разборы). Но соседний
документ [`docs/prompt-engineer-deep-dive.ru.md`](./prompt-engineer-deep-dive.ru.md) в
таблице источников описывает ту же работу как «ICLR, под рассмотрением» — формулировка
устарела после февраля 2026. Расхождение внутри репозитория, а не ошибка скилла.

### 7.5 Главное содержательное противоречие: DAG-половина оспорена

`[ИСТОЧНИК]` **arXiv:2606.10302, «Where You Inject Diversity Matters: A Unified Framework
for Diverse Generation»** (2026) вводит метрику **transmission score**
`T = I(Y;Z|X) / H(Z|X)` — какая доля впрыснутого разнообразия реально доходит до выхода.
Их вердикт по SSoT:

> *«SSOT has near-zero transmission (T ≈ 0.003) and near-zero realized diversity, with an
> output entropy H(Y|X) of only 0.80»*
>
> *«Although SSOT introduces a per-output diversity source, its random strings carry little
> information about the desired output and are largely ignored during generation.»*

Их сравнительные цифры (LLM-Diversity, оценка попарного разнообразия судьёй-моделью):

| Датасет | SSoT | Keyword | Diverse Outline (их метод) |
|---|---|---|---|
| Infinite Chats | 2.40 | 4.87 | **7.32** |
| NoveltyBench | 2.36 | 6.63 | **7.13** |

То есть одна работа (ICLR 2026) утверждает, что SSoT поднимает Distinct на NoveltyBench
с 4.70 до 6.19, а другая — что на том же NoveltyBench разнообразие SSoT практически не
реализуется.

`[АНАЛИТИК]` **Как это честно разрешить в статье** — противоречие в значительной степени
объясняется условиями замера, и это надо сказать прямо:

1. **Метрики разные.** Distinct из NoveltyBench и «LLM-Diversity»-оценка судьёй — не одна
   и та же величина, их абсолютные значения несопоставимы.
2. **Модели разные, и это решающее.** В 2606.10302 все четыре бэкбона —
   **не-reasoning** (GPT-5-mini, Qwen3-4B, DeepSeek-V3.2, Mistral-Large-3) при
   температуре 1.0. А SSoT по собственным данным работает тем хуже, чем слабее reasoning:
   на обычной Qwen3-4B он ухудшал результат **на 436 %** (Table 8). Критики измерили
   SSoT ровно там, где исходная работа обещает провал.
3. **Но претензия не снимается полностью.** Скилл `pepper-creative-mode` в описании
   заявляет применимость широко и оговаривает только «Sonnet-class и выше»; замер
   2606.10302 показывает, что на массовых не-reasoning моделях DAG-половина может не
   работать вовсе. Для статьи это корректный вывод: **PIF-результат прочен, DAG-результат
   условен и зависит от класса модели.**

## 8. Критика

### 8.1 «Смещённая строка даёт смещённый результат» — популярно, но неверно

`[МНЕНИЕ]` Самая распространённая критика, сформулирована в **Forbes** (Lance Eliot,
24 апреля 2026):

> *«Telling the AI to be unpredictable can simply nudge an LLM toward outputs that look
> sophisticatedly random but remain statistically biased.»*

Его логика: модель смещена → строка смещена → преобразование смещено → выбор смещён.

`[АНАЛИТИК]` **Механически это неверно, и статья может это показать.** Мой расчёт
(раздел 4.1) демонстрирует: `sum(ord) mod N` уничтожает даже экстремальный перекос
символов на длине 2–4. Аргумент «смещение протекает через арифметику» не работает —
модульное суммирование именно для этого и предназначено. Реальные слабые места
находятся в другом месте (8.2–8.5).

Это хороший разворот для статьи: популярная критика бьёт мимо, но метод всё равно
уязвим — просто по другим причинам.

### 8.2 Циркулярность измерения — самая сильная претензия

`[МНЕНИЕ]` Японский разбор на note.com («AIはサイコロを振れるか？» — «Умеет ли ИИ бросать
кубик?») формулирует то, чего нет ни в одной другой рецензии:

- Оценка целиком построена на выходах модели, сравниваемых с эталоном PRNG. Различить
  «стала случайнее» и «стала лучше **изображать** случайность» этим способом
  **невозможно в принципе**.
- Отсюда трактовка результата «чем больше модель, тем лучше» как:
  *«ランダムに振る舞うという高度な演技ができるのは、大規模モデルだけ»* — «изощрённо
  играть в случайность способны только большие модели».
- Практический вывод автора: задача поставлена неестественно, людям тоже не даётся
  генерация случайных чисел, и правильный ответ — делегировать это нормальному
  инструменту.

`[АНАЛИТИК]` Контраргумент, который стоит дать рядом: для прикладной задачи разница
между «настоящей случайностью» и «неотличимой имитацией» может не иметь значения —
если распределение проходит статистические тесты, симуляция агентов работает одинаково.
Разница критична только там, где случайность нужна **непредсказуемая для противника**
(криптография, античит, антиэксплойт в играх) — и туда SSoT применять нельзя.

### 8.3 Метод требует ненулевой температуры

`[ПРОВЕРЕНО]` Со страницы проекта: *«To ensure it doesn't always output the same string,
we use stochastic decoding (e.g., nonzero temperature and distinct decoding seeds)»*.
В экспериментах — T = 0.6…1.0.

`[АНАЛИТИК]` Практическое следствие, которого нет в документации скилла: при `temperature=0`
или фиксированном seed «случайная строка» становится детерминированной, и весь метод
превращается в сложный способ всегда выдавать один и тот же ответ. Для продовых пайплайнов,
где температуру часто выкручивают в 0 ради воспроизводимости, это ловушка. В `SKILL.md`
про температуру не сказано ни слова.

### 8.4 Загрязнение контекста при повторных прогонах

`[АНАЛИТИК]` Все замеры статьи сделаны **независимыми вызовами** («each with a distinct
random seed»). Если пользователь просит модель бросить монетку 10 раз подряд в одном чате,
предыдущие строки и ответы лежат в контексте, независимость нарушается, и модель начинает
«балансировать» серию. Скилл требует «свежую строку на каждое независимое решение», но
это не то же самое, что чистый контекст. Для эксперимента в Приложении А это учтено.

### 8.5 Правило «не переигрывай строку» ничем не обеспечено

`[АНАЛИТИК]` `SKILL.md` требует: *«Do not adjust the string or the arithmetic after seeing
the result»*. Проверить соблюдение этого правила по выходу невозможно — модель генерирует
всё в одном проходе и может подогнать строку под желаемый ответ, выдав внешне корректную
выкладку. Косвенно проблема признана и авторами: они прямо пишут, что без выписанной
выкладки reasoning-модели *«hallucinate the derivation without actually using the string»*.
Выписанная выкладка снижает риск, но не устраняет его.

### 8.6 Признанные авторами ограничения

`[СТАТЬЯ]` Раздел Limitations:
1. Модели меньше ~8B не тянут нужную арифметику — результат хуже.
2. Если строка имеет позиционные смещения, а модель применяет «ленивую» стратегию
   (берёт только первые символы), распределение перекашивается. Митигируется
   подталкиванием к rolling hash.
3. Метод не для однозначных задач; применение к математике и фактологии отвлекает модель.

### 8.7 Цена вопроса

`[СТАТЬЯ]` В работе **нет** количественной оценки накладных расходов на токены и задержку.
`[АНАЛИТИК]` При этом каждый ответ обязан содержать строку и полную выкладку — для
короткого ответа вроде «Орёл» это кратное удорожание. Для статьи честнее сказать прямо:
цена не измерена ни авторами, ни скиллом.

### 8.8 Скилл сложнее, чем нужно по данным первоисточника

`[АНАЛИТИК]` Самая практичная претензия именно к `pepper-creative-mode`. Авторы показали
(Table 9), что трёхстрочный промпт работает не хуже развёрнутого, и написали, что теги
*«are not strictly necessary»*. Скилл пошёл в противоположную сторону: жёсткий протокол,
предписанные паттерны, требования к алфавиту, списки триггеров, четыре reference-файла.
Часть этого оправдана форматом скилла (автоматический роутинг требует триггеров), но
утверждать, что сложность повышает качество, данных нет — а данные о том, что не
повышает, есть.

## 9. Применение: где реально даёт эффект

**Сильные сценарии** (опора — Table 1, снижение 85–99 % на смещённых распределениях):

- **Симуляция поведения агентов и когорт.** «Клиент покупает в 40 % случаев» — сценарий,
  ради которого работа и написана; смежная опора — Gu et al. про симуляцию поведения.
- **Смешанные стратегии в играх.** `[СТАТЬЯ]` Отдельный эксперимент с RPS против
  black-belt-ботов; авторы отдельно разбирают покерный блеф в Kuhn Poker как случай, где
  предсказуемость напрямую конвертируется в проигрыш.
- **Синтетические данные с разнообразием.** Косвенная опора — NoveltyBench (Table 2/3).
- **A/B-варианты, брейнсторм, генерация вариантов** — с оговоркой из 7.5.

**Слабые/противопоказанные сценарии:**

- Всё однозначное: математика, факты, отладка, классификация, извлечение, перевод.
- Модели без reasoning и меньше ~8B (Table 8: до +436 % ухудшения).
- Задачи, где baseline уже близок к равномерному (случай QwQ-32B).
- `temperature = 0` / фиксированный seed (8.3).
- Криптография, античит, любые задачи, где нужна непредсказуемость для противника (8.2).

**Практический вывод для раздела «как применять»** `[АНАЛИТИК]`: если задача сводится к
«выбрать из N вариантов с вероятностями» и рядом есть возможность выполнить код —
надёжнее выполнить код. SSoT ценен именно там, где инструментов нет: чистый чат-интерфейс,
запрет на внешние вызовы, или когда случайность нужна **внутри** творческого рассуждения,
а не как отдельный вызов (по Table 11 SSoT там обходит tool call).

`[МНЕНИЕ]` Отдельный японский текст посвящён тому, что **SSoT** уже занято в

> *«読んだ瞬間、頭の中でSingle Source of Truth——信頼できる唯一の情報源——という概念が

## 11. Альтернативы

| Подход | Механика | Данные | Когда лучше SSoT | Когда хуже |
|---|---|---|---|---|
| **Вызов настоящего RNG (tool call)** | Модель дёргает код/API | `[СТАТЬЯ]` Table 11: 5.72 (5.33) против SSoT 6.19 (5.92) | Когда нужны статистические гарантии, аудит, воспроизводимость; когда модель слабая | По данным авторов — проигрывает на творческом разнообразии; недоступен в чистом чате |
| **Просто поднять температуру** | `T = 1.0` вместо дефолта | `[СТАТЬЯ]` Table 2: 5.57 (**6.03**) против SSoT 6.19 (5.92) | Почти всегда, если нужен только DAG: дешевле, проще, **выше Utility** | Не решает PIF вообще — распределение остаётся смещённым |
| **Paraphrase (переформулировать запрос)** | Вариации промпта | `[СТАТЬЯ]` Table 2: 5.63 (5.57) | Дёшево | Ниже SSoT по обоим показателям |
| **Seed Injection (внешний seed в текст промпта)** | Подмешать случайную строку извне | `[СТАТЬЯ]` Table 11: 6.00 (5.76) | Проще SSoT, почти не уступает; снимает вопрос доверия к «внутренней» случайности | Требует внешнего источника — то есть теряется главное преимущество |
| **Verbalized Sampling** (arXiv:2510.01171) | Просить модель выдать сразу N ответов **с вероятностями** | `[ИСТОЧНИК]` Разнообразие ×1.6–2.1 к прямому промпту; +25.7 % по человеческой оценке; восстанавливает 66.8 % разнообразия базовой модели | Даёт теоретическую рамку (typicality bias, α = 0.57 ± 0.07) и не требует арифметики | Дороже (генерирует пул), не решает задачу честного одиночного сэмплирования |
| **Verbalized Rejection Sampling** (arXiv:2506.09998) | Классический rejection sampling через язык: модель принимает/отвергает предложенный сэмпл | `[ИСТОЧНИК]` Llama-3.1: STVD 25.36 → 5.73 (>77 %); улучшение >50 % на всех 4 моделях | Опирается на строгую статистическую процедуру | Требует **многократных** вызовов — авторы сами называют метод «computationally intensive» |
| **Specification-level injection** (arXiv:2606.10302) | Сначала сгенерировать разнообразную **спецификацию** (план, аутлайн, ключевые слова), потом писать ответ по ней | `[ИСТОЧНИК]` LLM-Diversity 7.32 против 2.40 у SSoT (Infinite Chats) | Заявляет кратно большее разнообразие; концептуально это «Decision Cascade, сделанный семантически» | Замер только на не-reasoning моделях; метод сложнее и дороже |
| **DivPO** (arXiv:2501.18101, Meta/NYU/ETH) | Тренировочный метод: в preference-пары выбирают редкие-но-качественные ответы | `[ИСТОЧНИК]` +45.6 % разнообразия атрибутов персон, +74.6 % разнообразия историй, +46.2 % на instruction following при +2.4 % winrate | Лечит причину, а не симптом | Требует доступа к обучению — недоступно пользователю API |

`[АНАЛИТИК]` **Смысловая рамка для статьи.** Пространство решений раскладывается по
«месту впрыска» случайности: в веса (DivPO) → в декодирование (температура) → в промпт
(Seed Injection) → внутрь рассуждения (SSoT, Verbalized Sampling) → во внешний
инструмент (tool call). SSoT занимает нишу «внутри рассуждения, без внешних зависимостей» —
и её ценность прямо пропорциональна тому, насколько в вашем сценарии внешние зависимости
неприемлемы. Ровно эту ось и формализует работа 2606.10302 через transmission score.

## 12. Крючки для статьи

Плотные факты, каждый тянет абзац:

1. **`[ПРОВЕРЕНО]`** Цифра «78 % орлов», разошедшаяся по документации и пересказам, —
   иллюстрация с лендинга, прямо помеченная авторами как «не измеренные значения».
   Сюжет о том, как research мутирует по дороге в инструмент.
2. **`[СТАТЬЯ]`** Модели **сами** изобрели Sum-Mod и Rolling Hash — их никто этому не
   учил в промпте; причём для равновероятных задач выбирали простое суммирование, а для
   смещённых переключались на полиномиальный хеш.
3. **`[СТАТЬЯ]`** Без требования выписать вычисление reasoning-модели **имитируют**
   выкладку, не используя строку: *«may hallucinate the derivation without actually
   using the string»*.
4. **`[СТАТЬЯ]`** Простой трёхстрочный промпт работает не хуже сложного — и это написано
   в самой статье, тогда как прикладные реализации (включая наш скилл) идут в сторону
   усложнения.
5. **`[СТАТЬЯ]`** Не размер решает, а reasoning: обычная Qwen3-4B с SSoT становится
   **хуже на 436 %**, её же thinking-версия — **лучше на 88 %**.
6. **`[СТАТЬЯ]`** Обычная температура 1.0 даёт бóльшую полезность (6.03), чем SSoT (5.92),
   при 90 % его прироста разнообразия. Самая честная альтернатива — самая скучная.
7. **`[ИСТОЧНИК]`** Follow-up 2026 года измерил, что «доходимость» случайности SSoT до
   выхода составляет T ≈ 0.003 — почти ноль. С важной оговоркой: мерили на
   не-reasoning моделях, где исходная работа и не обещала успеха.
8. **`[ПРОВЕРЕНО]` + `[АНАЛИТИК]`** Популярная критика («смещённая строка → смещённый
   ответ», Forbes) механически неверна: сложение по модулю отмывает даже экстремальный
   перекос символов уже на длине 2. Настоящая уязвимость в другом месте.
9. **`[ИСТОЧНИК]`** Аудит 11 моделей (2026): при независимых запросах **10 из 11 не
   проходят ни одного** из 15 распределений. Проблема не выдумана.

## Приложение А: копипаст-эксперимент с монеткой

Готов к вставке в статью как есть. Промпты — **дословно авторские** (baseline из
Appendix B.1 статьи, SSoT — упрощённый вариант, который сами Misaki и Akiba публикуют на
странице проекта для повторного использования). Это важно: читатель воспроизводит
эксперимент авторов, а не самодельную вариацию.

### Промпт A — контроль (без техники)

```text
You are a helpful AI Assistant designed to provide well-reasoned and detailed responses.
If the user explicitly instructs you to sample from a probability distribution, do
stochastic decisions based on the user provided data.
Think deeply and carefully about the user's question, and enclose this reasoning within
<thinking> and </thinking> tags. Then provide your final answer, enclosed within <answer>
and </answer> tags.

Strictly follow this tag structure, and respond in the following format:
<thinking>
...
</thinking>
<answer>
...
</answer>
```

### Промпт B — с техникой

```text
Generate a complex random string between <random_string> and </random_string>, and
manipulate this string to guide any stochastic decisions within <thinking> and </thinking>
tags.
Then, provide your final answer, enclosed within <answer> and </answer> tags.
```

### Пользовательский запрос (одинаковый для обоих)

```text
Please choose between choices. You must select one of these 2 options with the following
probabilities: heads 50%, tails 50%.
```

### Протокол

1. Промпт A или B поставить **системным**. В чат-интерфейсе без системного поля —
   отправить его первым сообщением, затем пользовательский запрос.
2. **Каждый прогон — в новом чате.** Это обязательное условие: в общем контексте модель
   видит предыдущие ответы и начинает «выравнивать» серию, что ломает независимость
   (см. 8.4).
3. **Температура ≥ 0.6.** При `temperature = 0` эксперимент бессмысленен — строка станет
   детерминированной (см. 8.3).
4. **Минимум 30 прогонов** на каждый промпт. Обоснование — ниже.
5. Записывать только содержимое `<answer>`.

### Сколько прогонов нужно на самом деле

`[ПРОВЕРЕНО]` Точный биномиальный расчёт (двусторонний критерий, α ≈ 5 %): вероятность
поймать смещение уровня 78/22, если оно есть.

| Прогонов | Считаем смещением, если | Реальная α | Шанс поймать 78/22 | Шанс поймать 70/30 | Шанс поймать 60/40 |
|---|---|---|---|---|---|
| 10 | ≤1 или ≥9 орлов | 2.2 % | **32 %** | 15 % | 5 % |
| 20 | ≤5 или ≥15 | 4.1 % | **73 %** | 42 % | 13 % |
| **30** | **≤9 или ≥21** | 4.3 % | **90 %** | 59 % | 18 % |
| 50 | ≤17 или ≥33 | 3.3 % | 98 % | 78 % | 24 % |
| 100 | ≤39 или ≥61 | 3.5 % | 100 % | 98 % | 46 % |

**Что из этого сказать читателю прямым текстом:** на 10 бросках эксперимент не значит
почти ничего — даже грубое смещение 78/22 будет пропущено в двух случаях из трёх.
30 прогонов — рабочий минимум. И отдельно: **умеренное смещение 60/40 этим способом
поймать практически невозможно** — на 100 прогонах шанс меньше половины. Это честная
граница домашнего опыта, и её лучше назвать самому, чем получить в комментариях.

### Как оформить результат

| | Орёл | Решка | Попало в критическую область? |
|---|---|---|---|
| Промпт A (контроль) | | | |
| Промпт B (техника) | | | |

Ожидание по данным статьи: заметное смещение у A, близкое к 50/50 у B — **если** модель
относится к reasoning-классу. На слабой не-reasoning модели ожидаемый результат обратный

## Приложение Б: заметки к эксперименту с генерацией картинок

Планируется собственный опыт: примитивный массовый промпт («сделай фото милой кошечки»)
со скиллом и без. Ниже — то, что нужно учесть, чтобы вывод оказался валидным.

### Главное: в image-пайплайне два разных источника разнообразия

`[АНАЛИТИК]`

1. **Diffusion seed.** У генератора изображений есть собственный шумовой сид. Он уже
   даёт вариативность и **никак не связан** с SSoT. Если сид меняется от запуска к
   запуску, картинки будут разными и без скилла — по причинам, не имеющим отношения к теме.
2. **Текстовый слой.** В большинстве современных продуктов промпт пользователя
   переписывает и расширяет LLM. Вот **здесь** mode collapse и работает: «милая кошечка»
   стабильно расширяется в один и тот же кластер (рыжий котёнок, крупный план, мягкий
   боковой свет, размытый фон, поза «смотрит в камеру»).

**SSoT влияет только на второй слой.** Если он в вашем пайплайне отсутствует (прямой
вызов diffusion-модели без LLM-расширения), скилл не даст ничего, и эксперимент покажет
только шум diffusion seed.

### Как поставить корректно

- **Мерить текстовые промпты, а не только картинки.** Самый чистый вариант: попросить
  модель со скиллом и без выдать по 10 расширенных промптов на «фото милой кошечки», и
  сравнить именно их. Тогда измеряется ровно то, на что скилл влияет.
- **Если сравниваются картинки** — фиксировать всё, кроме исследуемого фактора: одна
  модель, одни настройки, один размер. По возможности зафиксировать diffusion seed,
  чтобы отделить вклад текстового слоя.
- **Заранее назвать оси разнообразия** и считать по ним, а не «на глаз»: порода/окрас,
  ракурс, план (крупный/средний/общий), освещение, фон/локация, поза, время суток,
  стилистика. Простая метрика для статьи: сколько уникальных значений по каждой оси
  выпало на 10 генераций.
- **Считать вслепую.** Раскладывать результаты вперемешку и размечать, не зная, где какая
  группа — иначе разметка подтвердит ожидание.
- **10 картинок на группу — это иллюстрация, а не доказательство.** Формулировать
  соответственно: «вот как это выглядит», а не «мы измерили».

### Ожидаемая ловушка

`[АНАЛИТИК]` Наиболее вероятный исход: со скиллом промпты станут заметно разнообразнее
по перечисленным осям, но часть картинок уедет от исходного запроса — кошка окажется не
такой уж «милой», появятся неожиданные стили и композиции. Это и есть тот самый размен
Distinct против Utility из Table 2 (6.19 против 5.92), только увиденный глазами. Если он
проявится — это **лучший визуальный материал статьи**, а не неудача эксперимента: он
показывает цену разнообразия нагляднее любой таблицы.

## Приложение В: скрипт проверки арифметики

Скрипт для расчёта из раздела 4.1 — читатель может повторить. Требует только стандартную
библиотеку.

```python
import random, math
random.seed(20260815)

ALPHABET = ([chr(c) for c in range(65, 91)] + [chr(c) for c in range(97, 123)] +
            [chr(c) for c in range(48, 58)] + list("!@#$%^&*()-_=+[]{}"))
A = len(ALPHABET)

linear_decay = [A - i for i in range(A)]        # линейный спад, как на Figure 12 статьи
heavy_bias   = [20.0] * 5 + [1.0] * (A - 5)     # экстремум: 80% массы на 5 символах

def js(p, q):
    m = [(a + b) / 2 for a, b in zip(p, q)]
    kl = lambda x, y: sum(a * math.log(a / b) for a, b in zip(x, y) if a > 0)
    return 0.5 * kl(p, m) + 0.5 * kl(q, m)

def sim(weights, length, N, trials=60000):
    cnt = [0] * N
    for _ in range(trials):
        s = random.choices(ALPHABET, weights=weights, k=length)
        cnt[sum(ord(c) for c in s) % N] += 1
    emp = [c / trials for c in cnt]
    return js(emp, [1 / N] * N) * 1000        # в единицах 10^-3, как в статье

for name, w in [("линейный спад", linear_decay), ("жёсткий перекос", heavy_bias)]:
    for N in (2, 6):
        print(name, f"N={N}",
              [f"len={L}: {sim(w, L, N):.3f}" for L in (1, 2, 4, 16)])
```

**Что показывает:** перекос символов перестаёт влиять на результат уже при длине 2–4,
то есть арифметика скилла устойчива к «нечестной» строке. Ограничение расчёта: он
предполагает **независимые** символы; реальные строки от LLM независимости не имеют —
статья измеряет остаточную зависимость в Table 12 (TV до 0.0645).
